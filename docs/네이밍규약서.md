# hailcast 인프라 — 네이밍 규약서

> **이름은 계약이다.** 여기 정한 문자열을 앱·ML·배포팀이 코드에 그대로 참조한다.
> 이 문서가 리소스 이름의 **단일 진실원천(SSOT)** 이다. 이름을 바꾸려면 **이 문서를 먼저 고치고** 팀에 공유한 뒤 코드를 바꾼다.
>
> 대상 레포: `project3-hailcast-infra` · 담당: 이미선 · 리전: `ap-northeast-2`(서울)

## 상태 표기 — 이 넷을 섞어 읽지 마라

| 태그 | 뜻 |
|---|---|
| **[확정]** | 코드에 있다. 값이 굳었다. 그대로 참조하면 된다 |
| **[미구현]** | **만들기로 했는데 아직 코드가 없다.** 누가·언제가 함께 적혀 있다 |
| **[안 함]** | **안 만들기로 결정했다.** 기다려도 안 나온다 |
| **[대기]** | 남의 답을 기다린다. 누구 답인지 적혀 있다 |

> **설계 근거·개정 이력은 이 문서에 없다** → `노트/작업/설계근거_인프라.md`

# 1. 네이밍 대원칙

```
<project_name>-<environment>-<리소스종류>[-<식별자>]
```
예) `hailcast-dev-vpc` · `hailcast-dev-subnet-public-2a` · `hailcast-dev-rds-postgres`

| 대상 | 규칙 | 안 지키면 |
|---|---|---|
| Terraform 변수 | snake_case | 팀 컨벤션 위반 |
| AWS 리소스 이름 | kebab-case | 대부분 리소스가 대문자·밑줄 불가 → apply 실패 |
| S3 버킷 이름 | 소문자+하이픈 · 밑줄 금지 · **전역 유일** | 이름 충돌 → **랜덤 접미사 필수** |
| 예측 지표(메트릭) | snake_case | scaler 가 읽는 JSON 키와 불일치 |

### access entry — 사람이 클러스터에 들어오는 문 **[미구현]**

**access entry = 사람이 클러스터로 들어온다. IRSA = 파드가 AWS 로 나간다. 섞지 마라.**

| 항목 | 값 |
|---|---|
| admin principal | `arn:aws:iam::<ACCOUNT_ID>:user/<USER>` ⚠️ **실제 값을 이 문서에 적지 마라 — 이 레포는 퍼블릭이다.** `terraform.tfvars`(gitignore)에만 |
| 접근 정책 ARN | `arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy` (**전체 ARN 그대로** — 짧은 이름은 동작 안 함) |
| access scope | `type = "cluster"` |
| Terraform 변수 | `cluster_admin_principal_arns` · `list(string)` · 기본 `[]` |
| `authentication_mode` | `API_AND_CONFIG_MAP` [확정 · `modules/eks/cluster.tf:25`] |
| `bootstrap_cluster_creator_admin_permissions` | `true` [확정 · `cluster.tf:26`] |

> ⚠️ **apply 를 실행한 principal 은 목록에 넣지 마라.** 같은 principal 이 두 access entry 에 들어가면 **apply 가 실패**한다("An IAM principal can't be included in more than one access entry"). `bootstrap … = true` 라 apply 주체는 **자동 등재**된다.
> → **첫 apply 를 내가 로컬에서 하므로, 목록에 나를 넣으면 안 된다.**

### IRSA 8종 [확정]

역할명·SA 이름은 **manifests 의 ServiceAccount 와 맺는 계약**이다. 파드가 다른 SA 로 뜨면 신뢰정책 `sub` 가 어긋나 **`AssumeRole` 이 거부되고 '권한 없음'** 이 된다.

| IRSA 역할명 | 연결 SA (`네임스페이스:이름`) | 권한 |
|---|---|---|
| `hailcast-dev-irsa-predict` | `hailcast:predict-sa` | S3 읽기 `models/*`·`weather/*`·`traffic/instances/*` · 읽기+쓰기 `predictions/*`·`dashboard/*`·`scaling/*` · **`s3:ListBucket`(버킷 자체)** · DynamoDB 쓰기 · `sqs:GetQueueAttributes`·`GetQueueUrl` |
| `hailcast-dev-irsa-call-api` | `hailcast:call-api-sa` | `sqs:SendMessage`·`GetQueueUrl` · S3 읽기 `calls/*` · 쓰기 `traffic/instances/*` |
| `hailcast-dev-irsa-worker` | `hailcast:worker-sa` | `sqs:ReceiveMessage`·`DeleteMessage`·`GetQueueUrl` · S3 읽기+쓰기 `calls/*` |
| `hailcast-dev-irsa-weather-cron` | `hailcast:weather-cron-sa` | S3 쓰기 `weather/*` **만** |
| `hailcast-dev-irsa-keda` | `keda:keda-operator` | `sqs:GetQueueAttributes` |
| `hailcast-dev-irsa-karpenter` | `kube-system:karpenter` | EC2 관리 · 중단 큐 수신 |
| `hailcast-dev-irsa-lbctrl` | `kube-system:aws-load-balancer-controller` | ALB 생성·관리 |
| `hailcast-dev-irsa-monitoring` | `monitoring:monitoring-sa` | CloudWatch 읽기 |

> 🚨 **배포팀 할 일 — manifests 에 ServiceAccount 정의가 현재 0건이다.** 위 SA 이름 그대로 만들어야 한다. **`weather-cron-sa` 는 새 이름이다.**

**S3 프리픽스 소유권 — IRSA 를 자르는 기준**

| 프리픽스 | predict | call-api | worker | weather-cron |
|---|---|---|---|---|
| `models/*` | 읽기 | – | – | – |
| `predictions/*` | 읽기+쓰기 | – | – | – |
| `weather/*` | 읽기 | – | – | **쓰기** |
| `traffic/instances/*` | 읽기 | **쓰기** | – | – |
| `dashboard/*` | 읽기+쓰기 | – | – | – |
| `scaling/*` | 읽기+쓰기 | – | – | – |
| `calls/*` | – | **읽기** | 읽기+쓰기 | – |

| 규칙 | 왜 |
|---|---|
| **`models/` 에 쓰기를 주지 마라** | 앱이 S3 의 pickle 을 `joblib.load` 한다 → `models/` 에 쓸 수 있는 자는 **predict 파드에서 임의 코드 실행(RCE)** 을 얻는다. 학습된 모델이 날아가는 것보다 나쁘다 |
| **predict 에 `s3:ListBucket` 필수** | `traffic/instances/` 아래 파드별 샤드를 **목록 조회로 훑어** 합산한다. `GetObject` 로는 안 된다. 대상은 **버킷 ARN 자체**(`/*` 붙이면 인가 안 됨) |
| **worker 는 `calls/*` 읽기도 필요** | 재수신 시 이미 저장됐는지 읽어 보고 안 덮어쓰는 **멱등 처리** |
| **call-api 에 `calls/*` 쓰기 금지** | 쓰는 쪽은 worker. call-api 가 쓰면 **처리 상태를 스스로 조작**할 수 있다 |
| **`predictions/*` 는 프리픽스 전체** | 이력(`predictions/history/*.json`)도 함께 올라간다. `latest.json` 만 지목하면 이력 업로드가 실패 |
| **`sqs:GetQueueUrl` 필요 (KEDA 제외)** | 앱은 큐 **이름**만 알고 URL 을 모른다 → 첫 호출 전에 `GetQueueUrl` 을 부른다. KEDA 는 ScaledObject 에서 `queueURL` 을 통째로 받으므로 불필요 |
| **`s3:CreateBucket` 안 줌** | 앱의 `auto_create` 가 전 서비스 기본 `false`. 버킷은 IaC 가 소유 |
| **`sqs:PurgeQueue` 절대 금지** | 앱 어댑터에 `purge_queue()` 코드가 잠복해 있다(호출부는 0건). 권한을 주면 시연 중 큐가 통째로 비워질 수 있다 |

> ⚠️ **권한이 없어도 `AccessDenied` 로 안 보인다.** 앱의 `exists()` 가 **모든 `ClientError` 를 삼키고 `False` 를 반환**하고, 읽기는 그 앞에 `exists()` 를 먼저 부른다. → 증상이 **"파일 없음"** 으로 뜬다. 권한 문제를 데이터 문제로 착각하게 된다.

> **`irsa-forecast` — [안 함].** 예측을 쓰는 일을 predict 가 하므로 `forecast-sa` 를 달 파드가 없다. 그 권한은 `irsa-predict` 에 있다.
>
> **`irsa-simulator` — [대기].** simulator 는 SQS 를 안 쓰지만, **`JSON_STORE_BACKEND=s3` 로 파드를 띄우면 `simulator/status.json` 을 S3 에 쓴다.** 셋 중 하나로 정해야 한다.
> ① K8s 에 안 띄운다 → 역할 불필요 ② 띄우되 `JSON_STORE_BACKEND=local` → 역할 불필요 ③ 띄우고 s3 백엔드 → **`irsa-simulator` 신설**(`s3:PutObject` on `simulator/*`) · IRSA 9종

> ⚠️ **ScaledObject 를 patch 하는 권한은 IRSA 가 아니라 K8s RBAC 이다. 두 체계를 섞지 마라.**
> **배포팀 할 일:** `hailcast:predict-sa` 에 `scaledobjects` 의 `get`·`patch` 를 주는 **Role + RoleBinding**. Role 은 네임스페이스 스코프라 **ScaledObject 가 predict 와 같은 네임스페이스(`hailcast`)** 에 있어야 한다.

> 🚨 **큐만 만들면 안 된다. EventBridge 규칙 5종이 있어야 큐에 메시지가 들어온다.** 없으면 큐가 영원히 비고 Karpenter 는 **에러 한 줄 없이** 빈 큐만 폴링한다 → Spot 회수 때 **파드가 그냥 죽는다.**
> ⚠️ **KMS 고객관리키(CMK) 금지.** SQS 관리형 SSE 만 쓴다. (CMK 를 쓰면 EventBridge 가 큐에 못 넣는다)
> ⚠️ **큐 이름(`hailcast-dev`) ≠ 클러스터 이름(`hailcast-dev-eks`).** 배포팀이 `settings.interruptionQueue` 로 **명시해서 넘겨야** 한다(§8-2).

## 5-6. CI/CD OIDC 역할

| 역할명 | 레포 | 용도 | 권한 | 상태 |
|---|---|---|---|---|
| `hailcast-dev-gha-ecr` | app | 빌드 → ECR push | ECR push 만 · sub = **`main`·`dev` ref 만** | [확정] |
| `hailcast-dev-gha-tf-plan` | infra | `terraform plan` — PR 마다 자동 | **읽기 전용**(`ReadOnlyAccess`) + tfstate **잠금 파일만** 쓰기 · sub = **`pull_request` 만** | [확정] |
| `hailcast-dev-gha-tf-apply` | infra | `terraform apply` — **승인 후에만** | **사실상 계정 관리자**(아래) · 리전 `ap-northeast-2`+`us-east-1` 로 제한 | [확정] |

**apply 역할을 맡는 조건 (신뢰정책에 박혀 있다 — 하나라도 다르면 `AssumeRole` 거부)**

| 항목 | 값 |
|---|---|
| GitHub environment | **`infra-apply`** ✅ 생성 완료(팀장 · 7/14) |
| 워크플로 파일 | **`.github/workflows/terraform.yml`** ([미구현]) |
| 브랜치 | **`dev`** |

> 🚨 **apply 역할은 '사실상 계정 관리자' 다. `AdministratorAccess` 를 안 붙였을 뿐이다.**
> `iam:*` 이 열려 있어, 탈취당하면 **유저를 안 만들고도** 외부 계정을 신뢰하는 역할을 새로 만들거나 이 역할의 신뢰정책을 고쳐 영속 백도어를 만들 수 있다. **유저 생성·액세스 키 `Deny` 는 그 경로를 못 막는다.**
> → **진짜 방어선은 IAM 이 아니라 신뢰정책이다.** environment + 워크플로 파일 + 브랜치를 전부 못 박았다.

> 🚨 **워크플로에 `pull_request_target` 을 쓰지 마라.** base 브랜치 컨텍스트에서 돌며 `id-token` 을 받으므로, plan 역할의 sub 가 `ref:refs/heads/dev` 로 나온다. 그 값을 허용해 두면 **외부인이 plan 역할 안에서 코드를 실행**할 수 있고, `ReadOnlyAccess` 로 tfstate 를 읽으면 **RDS 비번이 평문으로 나온다.** 그래서 plan 의 sub 를 **`pull_request` 하나로만** 좁혔다.

> ⚠️ **`envs/dev/main.tf` 의 `tfstate_bucket`·`tfstate_key` 는 `backend.tf` 와 같은 값이어야 한다.** 어긋나면 plan 이 잠금을 못 걸어 죽는다.
> ⚠️ **plan 역할의 tfstate 쓰기는 `<key>.tflock` 하나뿐이다.** 버킷 전체에 주면 state 를 덮어써 **다음 apply 가 리소스를 파괴하게** 만들 수 있다.
> ⚠️ **plan 역할도 DB 비밀번호를 볼 수 있다.** tfstate 에 평문으로 들어가기 때문이다.

> 🚨 **CI 로 apply 하기 전에 §5-3 의 access entry 를 먼저 넣어라.** `bootstrap_cluster_creator_admin_permissions = true` 라 **클러스터를 만든 principal 하나만** 자동으로 cluster-admin 이 된다. CI 가 첫 apply 를 하면 그 principal 이 `gha-tf-apply` 역할이고, **사람은 아무도 `kubectl` 을 못 쓴다.**
> → **첫 apply 는 로컬에서 사람이 한다**(그래야 `gha-tf` 역할이 생긴다 · 닭-달걀). 그러면 그 사람이 자동 등재된다.

# 6. 태그 규약

## 6-1. 자동 발견 태그 [확정] — 빠지면 조용히 오작동

| 태그 키 = 값 | 붙일 대상 | 누가 읽나 |
|---|---|---|
| `kubernetes.io/role/elb = 1` | public 서브넷 | ALB Controller |
| `kubernetes.io/role/internal-elb = 1` | private 서브넷 | ALB Controller (내부 LB) |
| `karpenter.sh/discovery = hailcast-dev` | private 서브넷 | Karpenter (노드 띄울 **곳**) |
| `karpenter.sh/discovery = hailcast-dev` | **노드 SG** (`hailcast-dev-sg-eks-node`) | Karpenter (노드에 달 **SG**) |

> ⚠️ **노드 SG 태그가 빠지면 앱이 DB 에 못 붙는다 — 에러 없이.** RDS 는 5432 를 '노드 SG 를 단 놈'에게만 연다. 그런데 앱 파드는 Karpenter 가 띄운 노드에 산다. Karpenter 는 SG 를 **태그 검색**으로 찾으므로, 태그가 없으면 그 노드는 노드 SG 를 못 달고 → **연결 타임아웃**만 뜬다.

**서브넷의 `kubernetes.io/cluster/hailcast-dev-eks = shared` — [안 함]** (레거시)

> 🚨 **혼동 금지 — 죽은 것은 '서브넷의 `= shared`', 살아 있는 것은 'Karpenter 가 만든 노드의 `= owned`'. 대상도 값도 다르다.**
> ⚠️ **배포팀이 `EC2NodeClass` 의 `tags` 에서 `kubernetes.io/cluster/hailcast-dev-eks = owned` 를 빼면** IRSA 정책의 IAM Condition 이 안 맞아 `RunInstances` 가 거부된다 → **노드를 한 대도 못 띄운다.**

## 6-2. 비용 태그 [확정] (`default_tags`)

| 태그 키 | 값 | 용도 |
|---|---|---|
| `Project` | `hailcast` | 프로젝트 단위 비용 집계 |
| `Environment` | `dev` | 환경 구분 |
| `ManagedBy` | `terraform` | 콘솔 수동 생성물과 구분 → 고아 리소스 추적 |

## 8-4. 예측 → 스케일 경로 (방식 B · S3 JSON)

**수행 주체 = predict 내장.** 별도 CronJob 이 아니라 predict 프로세스 안의 스케줄러 2개가 한다.

| | 무엇을 | 주기 (앱 기본값) |
|---|---|---|
| `ForecastScheduler` | 예측 → `predictions/latest.json` | **4시간** |
| `ScalingScheduler` | JSON 읽어 ScaledObject patch | **60초** |
| `weather-cron` | Open-Meteo 수집 (별도 서비스) | **4시간** |

**파드 수 결정** = `ceil(예측수요 / scaling_demand_per_pod) + scaling_buffer_pods`, `[1, 10]` 로 clamp.
앱 기본값 `demand_per_pod = 500` · `buffer = 1`. → 예측이 float 여도 파드 수는 정수로 나온다.

> ⚠️ **`500` 은 "1시간당 수요 500" 이다** (예측값이 60분 창 기준). **30분으로 착각하면 파드당 수용치를 절반으로 잘못 잡는다.**

> 🚨 **[대기 — 앱팀] 예측 주기(4시간)와 만료(1시간)가 충돌한다. 선제 스케일링이 75% 시간 동안 불발된다.**
> scaler 는 **1시간보다 오래된 예측으로는 스케일하지 않는다**(`prediction_max_age_seconds = 3600`). 그런데 예측을 **4시간마다** 만든다 → **4시간 중 3시간은 예측이 만료돼** 스케일링이 통째로 건너뛰어진다. 로그에 `prediction too old` 만 남고 파드는 그대로다.
> **둘 중 하나를 정해야 한다.** ① 예측 주기를 30분으로 줄인다 ② `PREDICTION_MAX_AGE_SECONDS` 를 4시간 이상으로 늘린다.
>
> ⚠️ **`weather-cron` 은 기본 CMD 가 루프 모드라 Deployment 로 뜬다.** CronJob 으로 돌리려면 `--once` 로 command 를 덮어써야 한다. **배포팀이 정해 달라.**
