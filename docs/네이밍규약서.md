# hailcast 인프라 레포 — 네이밍 규약서

> **이름은 곧 계약이다.** 여기 정한 문자열을 앱·ML·배포팀이 코드에 그대로 참조한다.
> 이 문서가 모든 리소스 이름의 **단일 진실원천(Single Source of Truth)**이다. 이름을 바꿔야 하면 **이 문서를 먼저 고치고** 팀에 공유한 뒤 코드를 바꾼다.
>
> 대상 레포: `project3-hailcast-infra` · 담당: 이미선, 유현상 · 리전: `ap-northeast-2`(서울)

---

# 1. 네이밍 대원칙
## 1-1. 이름 공식

거의 모든 AWS 리소스 이름은 아래 한 공식으로 만들어집니다. 

```
<project_name>-<environment>-<리소스종류>[-<식별자>]
```

예) `hailcast-dev-vpc` · `hailcast-dev-subnet-public-2a` · `hailcast-dev-rds-postgres`

## 1-2. 문자 규칙 (지키지 않으면 apply가 실패)
| 대상 | 규칙 | 이유 |
|-------------------|-----------------------------------------|------------------------------------------------|
| Terraform 변수 | snake_case (소문자+밑줄) | HCL 관례 · 팀 코드 컨벤션(2차 계승) |
| AWS 리소스 이름   | kebab-case (소문자+하이픈)              | 대부분 AWS 리소스가 대문자·밑줄 불가           |
| S3 버킷 이름      | 소문자+하이픈, 밑줄 금지, **전역 유일** | 전 세계에서 하나뿐이어야 함 → 랜덤 접미사 필수 |
| 예측 지표(메트릭) | snake_case                              | Prometheus 관례 · KEDA 쿼리와 정확히 일치      |

# 2. 뿌리 변수 (envs/dev)
모든 이름과 태그가 이 세 변수에서 파생됩니다. envs/dev/variables.tf(또는 terraform.tfvars)에 최상단으로 선언합니다.

| 변수명 | 확정 값 | 타입 | 설명 |
|--------------|----------------|----------|--------------------------------------------------|
| project_name | hailcast       | string   | 모든 리소스 이름의 앞머리 · default_tags Project |
| environment  | dev            | string   | 환경 식별자 (단일 환경)                          |
| aws_region   | ap-northeast-2 | string   | 서울 리전 (전 리소스 공통)                       |

> 💡 이번 프로젝트는 **데모용 단일 환경**입니다. dev 하나로 통일하면 tfstate·태그·비용이 2배로 늘지 않습니다.

# 3. tfstate 원격 백엔드 (0순위 · Terraform 부트스트랩)
팀 7명이 같은 상태 파일(tfstate)을 공유해야 협업이 됩니다. 이 버킷·테이블은 Terraform이 스스로 못 만드는 '닭-달걀' 문제라 **버킷 생성 단계만 backend 없이(로컬 상태로) 부트스트랩** 합니다. 만든 뒤 정확한 문자열을 backend.tf에 박습니다.

| backend.tf 항목 | 확정 값 | 설명 |
|---------------------|---------------------------|-------------------------------------------------------------|
| bucket              | hailcast-dev-tfstate-a1b2 | 상태 저장+잠금 전용 버킷 (뒤 4자리는 실제 생성 값으로 교체) |
| key                 | dev/terraform.tfstate     | 상태 파일 경로 (환경 하나라 경로도 하나)                    |
| region              | ap-northeast-2            | 버킷 리전                                                   |
| use_lockfile        | true                      | S3 자체 잠금으로 동시 apply 방지 (DynamoDB 대체)            |
| encrypt             | true                      | 상태엔 시크릿이 평문으로 들어가므로 암호화 필수             |

> 💡 부트스트랩으로 버킷을 만든 인프라 담당이 생성된 **실제 버킷 이름(랜덤 접미사 포함)**을 확인해 backend.tf에 반영합니다. 만든 사람과 코드 반영자가 다르면 그 이름만 공유하면 됩니다. (use_lockfile은 Terraform 1.11+ 필요)

## 5-3. eks 모듈 — 클러스터 · 노드 · OIDC · IRSA
| 리소스 | 이름 / 값 | 비고 |
|------------------------|----------------------------|------------------------------------------------|
| EKS 클러스터           | hailcast-dev-eks           | cluster_version = 1.35 (표준지원 ~2027-02 · 착수 시 재확인) |
| System 노드그룹        | hailcast-dev-eks-system-ng | 관리형 · CoreDNS·Karpenter·KEDA·ArgoCD 호스팅  |
| Karpenter NodePool     | default                    | 앱 노드는 전부 Karpenter가 0부터 공급 [설계] |
| Karpenter EC2NodeClass | default                    | 노드 AMI·서브넷·SG 템플릿                      |
| OIDC Provider          | (EKS가 자동 생성)          | IRSA 전제 · enable_irsa=true 한 줄             |

**IRSA 역할** — 파드마다 발급하는 '제한된 사원증'. 신뢰관계에 클러스터 OIDC provider ARN이 박히므로 **eks 모듈에 함께 둔다**(별도 security 모듈로 빼면 OIDC 의존 때문에 생성 순서가 꼬임 = chicken-egg). 아래 역할명·SA는 manifests의 serviceaccount.yaml과 맺는 계약이다.

| IRSA 역할명 | 연결 SA (네임스페이스:이름) | 권한 범위 |
|---|---|---|
| `hailcast-dev-irsa-predict` | `hailcast:predict-sa` | S3 모델 읽기 + DynamoDB 쓰기 |
| `hailcast-dev-irsa-call-api` | `hailcast:call-api-sa` | SQS 콜 큐 송수신 |
| `hailcast-dev-irsa-monitoring` | `monitoring:monitoring-sa` | CloudWatch 읽기 |
| `hailcast-dev-irsa-karpenter` | `kube-system:karpenter` | EC2 관리 + 중단 큐 수신 |
| `hailcast-dev-irsa-lbctrl` | `kube-system:aws-load-balancer-controller` | ALB 생성·관리 |
| `hailcast-dev-irsa-forecast` | `hailcast:forecast-sa` | S3 예측 JSON 읽기·쓰기 (예측 배치 CronJob) |

> 💡 **`keda-scaler-updater` CronJob 권한:** S3 읽기는 **`hailcast-dev-irsa-forecast` 역할을 공유**(별도 읽기 전용 역할 안 만듦 · 데모 범위 YAGNI), ScaledObject 수정은 **K8s RBAC**(`scaledobjects`에 `get`·`patch`)로 처리한다. 두 체계를 섞지 말 것 — S3 접근은 IRSA(AWS 권한), ScaledObject patch는 RBAC(K8s 권한). (운영 시 읽기 전용 역할 분리는 개선과제)

| 리소스 | 이름 / 값 | 비고 |
|----------------------------------|---------------------------|------------------------------------------------|
| RDS (PostgreSQL)                 | hailcast-dev-rds-postgres | db.t3.micro · 콜 기록 · Single-AZ              |
| DB 서브넷 그룹                   | hailcast-dev-db-subnet-group | RDS를 프라이빗 서브넷(2a·2c)에 배치 · 서브넷그룹은 **≥2 AZ 필수** |

> 💡**Karpenter 중단 큐는 Spot을 쓰는 이상 필수.** 이 큐가 없으면 중단 처리가 아예 꺼져, 시연 중 Spot 노드가 회수될 때 파드가 그냥 죽습니다. 관례상 큐 이름을 클러스터 이름(hailcast-dev)과 동일하게 둡니다. (출처: Karpenter 공식 문서 — interruption queue 미설정 시 handling 비활성화)

**Secrets · 설정** — DB 비번은 Secrets Manager, 비밀 아닌 설정은 무료 Parameter Store. RDS와 함께 **data 모듈에 둔다**(클러스터와 무관).

| Secrets / 설정 | 이름 / 값 | 비고 |
|---|---|---|
| Secrets Manager (DB 비번) | `hailcast-dev-rds-postgres-credentials` | random_password 자동생성 → 보관 · RDS 인스턴스명 + `-credentials`(코드값 일치) |
| Parameter Store (DB 주소 등) | `/hailcast/dev/rds/endpoint` | 비밀 아닌 설정 → 무료 Parameter Store |

> 💡 진짜 비밀번호만 Secrets Manager(유료), DB 주소 같은 '비밀 아닌 설정'은 무료 Parameter Store로 나눠 담으면 비용이 줄어든다.

## 5-7. 엣지 — Route53 · CloudFront · ACM
> 데모는 **ALB 자동 발급 주소(`*.elb.amazonaws.com`)로도 접속 가능** → 엣지는 **커스텀 도메인·HTTPS·CDN을 원할 때만**. 착수 순서는 **ALB가 뜬 뒤(클러스터→ALB Controller→Ingress)**. 도메인은 보유/구매하거나 안 살 수도 있어 **`edge_domain` 변수(TBD)**로 둔다.

| 리소스 | 이름 / 값 | 비고 |
|---|---|---|
| Route53 호스티드 존 | `var.edge_domain` (TBD) | 보유·구매 도메인. **비워두면 ALB 주소 사용**(엣지 미적용) |
| ACM 인증서 (ALB용) | hailcast-dev-acm-alb | 리전 **ap-northeast-2**(서울) |
| ACM 인증서 (CloudFront용) | hailcast-dev-acm-cf | ⚠️ 리전 **us-east-1**(버지니아) **필수** — CloudFront는 us-east-1 인증서만 인식 |
| CloudFront 배포 | hailcast-dev-cloudfront | 오리진=ALB · alias=`edge_domain` |

> 💡 `edge_domain`을 비워두면(기본 ALB 주소) 나머지가 안 깨진다. 도메인→ALB 레코드 연결은 **`external-dns` 애드온(manifests)** 또는 terraform `data`로 ALB 참조. **ACM은 ALB(서울)·CloudFront(버지니아) 두 리전에 각각** 만들어야 하는 점 주의.

# 6. 태그 규약 (기능 태그 + 비용 태그)
## 6-1. 서브넷 자동 발견 태그 (기능용 — 빠지면 몇 시간 디버깅)
Karpenter와 ALB Controller는 '어느 서브넷에 자원을 만들까'를 **태그를 보고 스스로 찾습니다.** 태그가 없으면 못 찾아 Ingress·노드가 안 뜹니다.

| 태그 키 = 값 | 붙일 서브넷 | 누가 읽나 |
|---------------------------------------------|-----------------|-------------------------------|
| kubernetes.io/role/elb = 1                  | public          | ALB Controller (외부 LB 위치) |
| kubernetes.io/role/internal-elb = 1         | private         | 내부 LB 위치                  |
| karpenter.sh/discovery = hailcast-dev       | private         | Karpenter (노드 띄울 곳)      |
| kubernetes.io/cluster/hailcast-dev-eks = shared | private     | EKS 소유 서브넷 표시 (★클러스터명과 정확히 일치) |

## 6-2. 공통 비용 태그 (default_tags — OpenCost·Budgets 근거)
OpenCost와 Budgets는 '이 비용이 누구 것이냐'를 태그로 판단합니다. providers.tf에 한 번 선언하면 모든 리소스에 자동으로 붙습니다.

| 태그 키 | 값 | 용도 |
|-------------|-----------|--------------------------------------------|
| Project     | hailcast  | 프로젝트 단위 비용 집계                    |
| Environment | dev       | 환경 구분                                  |
| ManagedBy   | terraform | 콘솔 수동 생성물과 구분 → 고아 리소스 추적 |

# 8. 팀 전체 공유 계약 (인프라 → 앱·ML·배포)
인프라가 만들고 **다른 팀이 코드에 그대로 참조**하는 이름들입니다. 이것이 어긋나면 다른 팀이 병렬로 나가지 못합니다. 착수 전 반드시 못 박습니다.

| 계약 항목 | 확정 값 | 만드는 쪽 → 쓰는 쪽 | 어긋나면 |
|------------------|------------------------------------------------------|-------------------------|------------------------------|
| 예측 지표 이름   | predicted_taxi_demand                                | ML → S3 JSON → scaler → KEDA    | 선제 스케일 조용히 불발      |
| K8s 네임스페이스 | hailcast                                             | 인프라 → 전원           | 배포 위치 혼선               |
| ECR 이미지 태그  | 커밋 SHA (\$GITHUB_SHA)                              | 앱 CI → manifests       | '지금 뭐가 도는지' 추적 불가 |
| SQS 콜 큐        | hailcast-dev-call-queue                              | 인프라 → 앱·KEDA        | 안전망 불발                  |
