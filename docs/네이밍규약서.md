# hailcast 인프라 레포 — 네이밍 규약서

> **이름은 곧 계약이다.** 여기 정한 문자열을 앱·ML·배포팀이 코드에 그대로 참조한다.
> 이 문서가 모든 리소스 이름의 **단일 진실원천(Single Source of Truth)**이다. 이름을 바꿔야 하면 **이 문서를 먼저 고치고** 팀에 공유한 뒤 코드를 바꾼다.
>
> 대상 레포: `project3-hailcast-infra` · 담당: 이미선, 유현상 · 리전: `ap-northeast-2`(서울)

---

# 1. 네이밍 대원칙
## 1-1. 이름 공식

거의 모든 AWS 리소스 이름은 아래 한 공식으로 만들어집니다. 

```
<project_name>-<environment>-<리소스종류>[-<식별자>]
```

예) `hailcast-dev-vpc` · `hailcast-dev-subnet-public-2a` · `hailcast-dev-rds-postgres`

## 1-2. 문자 규칙 (지키지 않으면 apply가 실패)
| 대상 | 규칙 | 이유 |
|-------------------|-----------------------------------------|------------------------------------------------|
| Terraform 변수 | snake_case (소문자+밑줄) | HCL 관례 · 팀 코드 컨벤션(2차 계승) |
| AWS 리소스 이름   | kebab-case (소문자+하이픈)              | 대부분 AWS 리소스가 대문자·밑줄 불가           |
| S3 버킷 이름      | 소문자+하이픈, 밑줄 금지, **전역 유일** | 전 세계에서 하나뿐이어야 함 → 랜덤 접미사 필수 |
| 예측 지표(메트릭) | snake_case                              | Prometheus 관례 · scaler 가 읽는 JSON 키와 정확히 일치 |

# 2. 뿌리 변수 (envs/dev)
모든 이름과 태그가 이 세 변수에서 파생됩니다. envs/dev/variables.tf(또는 terraform.tfvars)에 최상단으로 선언합니다.

| 변수명 | 확정 값 | 타입 | 설명 |
|--------------|----------------|----------|--------------------------------------------------|

| environment  | dev            | string   | 환경 식별자 (단일 환경)                          |

> 💡 이번 프로젝트는 **데모용 단일 환경**입니다. dev 하나로 통일하면 tfstate·태그·비용이 2배로 늘지 않습니다.

# 3. tfstate 원격 백엔드 (0순위 · Terraform 부트스트랩)
팀 7명이 같은 상태 파일(tfstate)을 공유해야 협업이 됩니다. 이 버킷·테이블은 Terraform이 스스로 못 만드는 '닭-달걀' 문제라 **버킷 생성 단계만 backend 없이(로컬 상태로) 부트스트랩** 합니다. 만든 뒤 정확한 문자열을 backend.tf에 박습니다.

| backend.tf 항목 | 확정 값 | 설명 |
|---------------------|---------------------------|-------------------------------------------------------------|
| bucket              | hailcast-dev-tfstate-a1b2 | 상태 저장+잠금 전용 버킷 (뒤 4자리는 실제 생성 값으로 교체) |
| key                 | dev/terraform.tfstate     | 상태 파일 경로 (환경 하나라 경로도 하나)                    |
| region              | ap-northeast-2            | 버킷 리전                                                   |
| use_lockfile        | true                      | S3 자체 잠금으로 동시 apply 방지 (DynamoDB 대체)            |
| encrypt             | true                      | 상태엔 시크릿이 평문으로 들어가므로 암호화 필수             |

> 💡 부트스트랩으로 버킷을 만든 인프라 담당이 생성된 **실제 버킷 이름(랜덤 접미사 포함)**을 확인해 backend.tf에 반영합니다. 만든 사람과 코드 반영자가 다르면 그 이름만 공유하면 됩니다. (use_lockfile은 Terraform 1.11+ 필요)

| 변수명 | 타입 | 예시 값 | 쓰는 모듈 |
|----------------------|--------------------|------------------|-----------------------|
| project_name         | string             | hailcast         | 전 모듈               |
| environment          | string             | dev              | 전 모듈               |
| aws_region           | string             | ap-northeast-2   | 전 모듈               |
| vpc_cidr             | string             | 10.0.0.0/16      | network               |
| public_subnet_cidrs  | map/list           | 10.0.0.0/20 …    | network               |
| private_subnet_cidrs | map/list           | 10.0.32.0/20 …   | network               |
| availability_zones   | list(string)       | [2a, 2c]       | network               |
| vpc_id               | string             | (network output) | eks · data |
| private_subnet_ids   | list(string)       | (network output) | eks                   |
| public_subnet_ids    | list(string)       | (network output) | eks(ALB)              |
| oidc_provider_arn    | string             | (eks output)     | eks 내부(IRSA)        |
| cluster_name         | string             | hailcast-dev-eks | 애드온 · IRSA         |
| cluster_admin_principal_arns | list(string) | `["arn:aws:iam::<ACCOUNT_ID>:user/<USER>"]` | eks (§5-3 access entry) |
| db_password          | string (sensitive) | TF_VAR로 주입    | data                  |

**IRSA 정책이 지목할 ARN (eks 모듈 입력)** — eks 모듈은 S3·SQS·DynamoDB를 **만들지 않고 ARN만 받아씁니다.** `vpc_id`를 network에서 받아쓰는 것과 똑같은 패턴입니다.

| 변수명 | 타입 | 예시 값 | 쓰는 모듈 |
|----------------------------------|--------|----------------------------------|-----------------------------------------|
| model_bucket_arn                 | string | (storage output)                 | eks · IRSA predict (읽기 `models/*`+`predictions/*` · 쓰기 `predictions/*` 만) |
| sqs_call_queue_arn               | string | (data output `sqs_queue_arn`)    | eks · IRSA call-api·worker·keda·predict |
| prediction_log_table_arn         | string | (data output)                    | eks · IRSA predict                      |
| karpenter_interruption_queue_arn | string | (data output `karpenter_queue_arn`) | eks · IRSA karpenter                 |
| enable_app_irsa                  | bool   | 기본 false → 위 4종 배선 후 true | eks · IRSA **앱 5종**(predict·call-api·worker·keda·karpenter) 스위치 |

> 💡 db_password 같은 민감 값은 tfvars에 평문 금지입니다. 로컬은 TF_VAR_db_password 환경변수, CI는 GitHub Secret으로 주입하고, 실제 저장은 Secrets Manager가 합니다

> 💡 **Terraform에서 자식 모듈은 형제 모듈을 볼 수 없습니다.** `modules/eks` 안에서 `module.storage.model_bucket_arn`이라고 쓸 수 없다는 뜻입니다(그런 이름은 그걸 선언한 루트 `envs/dev`에만 존재합니다). 그래서 모듈 사이의 값 전달은 **루트가 output을 읽어 다음 모듈의 변수로 넘기는 방법 하나뿐**입니다.
>
> ```hcl
> # envs/dev/main.tf — 루트가 '중계'한다
> module "eks" {
>   source = "../../modules/eks"
>
>   enable_app_irsa                  = true
>   model_bucket_arn                 = module.storage.model_bucket_arn   # storage → eks
>   sqs_call_queue_arn               = module.data.sqs_queue_arn         # data    → eks
>   prediction_log_table_arn         = module.data.prediction_log_table_arn
>   karpenter_interruption_queue_arn = module.data.karpenter_queue_arn
> }
> ```

> 💡 ⭐ **`enable_app_irsa` 스위치가 왜 따로 있나 — "ARN이 null인지"로 판단하면 plan이 죽기 때문입니다.** storage·data의 output은 리소스가 아직 없는 **첫 plan에서 '미상(unknown)'** 입니다. 미상값에 `!= null`을 걸면 결과도 미상이 되고, 그걸 `for_each`·`count` 조건에 쓰면 **`Invalid for_each argument`로 plan 자체가 실패**합니다. 그래서 판단 근거를 '값'이 아니라 **plan 시점에 확정되는 리터럴 불리언**으로 둡니다. (스위치만 켜고 ARN을 빠뜨리면 변수 `validation`이 plan에서 이름을 찍어 막아 줍니다.)

## 5-3. eks 모듈 — 클러스터 · 노드 · OIDC · IRSA
| 리소스 | 이름 / 값 | 비고 |
|------------------------|----------------------------|------------------------------------------------|
| EKS 클러스터           | hailcast-dev-eks           | cluster_version = 1.35 (표준지원 ~2027-02 · 착수 시 재확인) |
| System 노드그룹        | hailcast-dev-eks-system-ng | 관리형 · CoreDNS·Karpenter·KEDA·ArgoCD 호스팅  |
| Karpenter NodePool     | default                    | 앱 노드는 전부 Karpenter가 0부터 공급 [설계] |
| Karpenter EC2NodeClass | default                    | 노드 AMI·서브넷·SG 템플릿                      |
| OIDC Provider          | (EKS가 자동 생성)          | IRSA 전제 · enable_irsa=true 한 줄             |
| 클러스터 access entry  | (아래 표)                  | **[설계]** 코드 미구현 — `aws_eks_access_entry` 0건 |

**클러스터 접근 권한 (access entry)** — 사람이 `kubectl`을 쓰려면 IAM principal이 클러스터의 **출입 명단**에 올라야 한다. IRSA와 **방향이 반대**다. 둘을 섞지 마라.

| 방향 | 무엇이 | 체계 |
|---|---|---|
| **IAM → 클러스터** (사람이 들어온다) | **access entry** | EKS Access Entry |
| **클러스터 → AWS** (파드가 나간다) | **IRSA** | IAM 역할 + OIDC |

| 항목 | 값 | 비고 |
|---|---|---|
| admin principal | `arn:aws:iam::<ACCOUNT_ID>:user/<USER>` | ⚠️ **실제 값을 이 문서에 적지 마라.** 이 레포는 **퍼블릭**이다 — 계정 ID + IAM 유저명이 공개된다. 값은 `terraform.tfvars`(gitignore)에만 |
| 접근 정책 ARN | `arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy` | **전체 ARN 그대로.** 짧은 이름으로는 동작하지 않는다 |
| access scope | `type = "cluster"` | 클러스터 전권 |
| Terraform 변수 | `cluster_admin_principal_arns` · `list(string)` · 기본 `[]` | eks 모듈 (§4) |
| `authentication_mode` | `API_AND_CONFIG_MAP` | 현행 유지 [실측 `modules/eks/cluster.tf:25`] |
| `bootstrap_cluster_creator_admin_permissions` | `true` | 현행 유지 [실측 `modules/eks/cluster.tf:26`] |

> 💡 ⭐ **왜 명단을 코드에 두나 — 안 두면 사람이 손으로 넣어야 하기 때문입니다.**
> `bootstrap_cluster_creator_admin_permissions = true` 는 **apply 를 실행한 principal 하나에게만** cluster-admin 을 자동으로 줍니다. AWS 문서상 그것이 **기본으로 만들어지는 유일한 access entry** 입니다("...which is the only entry created by default").
> **AWS 권한(IAM)과 클러스터 안 권한(K8s)은 별개 체계입니다.** `AdministratorAccess` 를 갖고 있어도 **클러스터 접근이 자동으로 주어지지는 않습니다.**
>
> ⚠️ **다만 '락아웃' 은 아닙니다 — 과장하지 마십시오.** `AdministratorAccess` 보유자는 `eks:CreateAccessEntry`·`eks:AssociateAccessPolicy` 권한을 이미 갖고 있어 **CLI 두 줄로 자기 자신을 명단에 넣을 수 있습니다.** AWS 가 이를 **접근 복구 절차로 문서화**해 두었습니다.
> → 그러니 근거는 "안 하면 프로젝트가 멈춘다" 가 아니라 **"안 하면 누군가 콘솔·CLI 를 손으로 만져야 하고, 그 수동 조작이야말로 IaC·GitOps 가 없애려는 drift 다"** 입니다. **명단은 코드로 선언합니다.**

> ⚠️ ⭐ **같은 principal 을 두 번 넣으면 apply 가 깨집니다.**
> AWS 문서: **"An IAM principal can't be included in more than one access entry."**
> `bootstrap ... = true` 인 상태에서 **클러스터를 만든 바로 그 principal** 을 `aws_eks_access_entry` 로 또 선언하면, EKS 가 이미 만들어 둔 엔트리와 겹쳐 apply 가 실패합니다.
> → **apply 주체는 목록에 넣지 마십시오.** CI 역할이 apply 하면 사람(IAM 유저)만 넣으면 되고, **사람이 로컬에서 apply 하면 그 사람은 이미 자동 등재되므로 목록에서 빼야 합니다.**

> 📌 **전제 — apply 주체가 아직 정해지지 않았습니다 (2026-07-14 현재 · 실측).**
> §5-6 의 `hailcast-dev-gha-tf` 역할은 **코드에 없고**(`modules/cicd` 가 만드는 역할은 `gha-ecr` 하나), `.github/workflows/terraform.yml` 은 **주석 한 줄짜리 빈 파일**입니다. 즉 **지금 apply 하면 사람이 로컬에서 하게 됩니다.**
> **apply 를 CI 로 옮기면** 자동 등재되는 것은 그 역할 하나뿐이고 **사람은 전원 명단에 없게 되므로**, 그때 이 절이 반드시 필요해집니다. CI 도입은 확정 사항입니다.

**IRSA 역할** — 파드마다 발급하는 '제한된 사원증'. 신뢰관계에 클러스터 OIDC provider ARN이 박히므로 **eks 모듈에 함께 둔다**(별도 security 모듈로 빼면 OIDC 의존 때문에 생성 순서가 꼬임 = chicken-egg). 아래 역할명·SA는 manifests의 serviceaccount.yaml과 맺는 계약이다.

| IRSA 역할명 | 연결 SA (네임스페이스:이름) | 권한 범위 |
|---|---|---|
| `hailcast-dev-irsa-predict` | `hailcast:predict-sa` | S3 **읽기 = `models/*` + `predictions/*`** · **쓰기 = `predictions/*` 만** + DynamoDB 쓰기 + `sqs:GetQueueAttributes`·`GetQueueUrl` |
| `hailcast-dev-irsa-call-api` | `hailcast:call-api-sa` | `sqs:SendMessage` + `sqs:GetQueueUrl` |
| `hailcast-dev-irsa-worker` | `hailcast:worker-sa` | `sqs:ReceiveMessage`·`DeleteMessage` + `sqs:GetQueueUrl` |
| `hailcast-dev-irsa-monitoring` | `monitoring:monitoring-sa` | CloudWatch 읽기 |
| `hailcast-dev-irsa-karpenter` | `kube-system:karpenter` | EC2 관리 + 중단 큐 수신 |
| `hailcast-dev-irsa-lbctrl` | `kube-system:aws-load-balancer-controller` | ALB 생성·관리 |
| `hailcast-dev-irsa-keda` | `keda:keda-operator` | `sqs:GetQueueAttributes` (큐 길이 조회) |

> 💡 ⭐ **`hailcast-dev-irsa-forecast` 는 폐기했습니다 (2026-07-13 · IRSA 8종 → 7종).**
> **결정 1(방식 B 수행 주체) = predict 내장** 전제입니다. 예측을 만들어 S3 에 쓰는 일을 별도 CronJob 이 아니라 **predict 프로세스 안의 스케줄러가** 합니다(`predict/dependencies.py:49-50`). 그러면 그 일을 하는 사원증도 `predict-sa` 하나뿐이라 `forecast-sa` 를 쓸 파드가 없습니다.
> → **`irsa-predict` 에 `s3:PutObject` on `predictions/*` 를 얹고 `irsa-forecast` 를 지웁니다.**
> ⚠️ **읽기와 쓰기를 다르게 자릅니다.** 읽기는 `models/*` **와** `predictions/*` 둘 다입니다(predict 가 `predictions/latest.json` 도 읽습니다). **쓰기만** `predictions/*` 로 좁힙니다. 상세는 §8.
> ⚠️ **`predictions/*` 프리픽스 전체를 줘야 합니다.** 이력(`predictions/history/*.json`)도 함께 올라갑니다(§8). `latest.json` 만 지목하면 이력 업로드가 `AccessDenied` 로 죽습니다.
> ⚠️ **`models/` 쓰기는 절대 주지 마십시오.** 예측 결과를 쓰는 쪽이 학습된 모델을 덮어써 날릴 수 있습니다.
> 앱팀이 CronJob 분리를 택하면 이 결정을 되돌립니다. 되돌리는 비용은 작습니다(역할 하나 추가 + 정책 경로 분리).
>
> ⏳ **`irsa-predict` 의 DynamoDB 쓰기는 앱 구현이 아직 0건입니다(오답노트 미구현). 그래도 권한은 남겨 둡니다.**
> `forecast` 를 지운 것과 이유가 다릅니다. **forecast 는 그 사원증을 달 파드 자체가 없습니다**(역할이 통째로 무의미). **DynamoDB 는 사원증(predict)은 있는데 그 권한을 쓸 코드가 아직 없을 뿐**입니다. 리소스(§5-4 `hailcast-dev-prediction-log`)와 이름 계약이 확정이라, 앱이 나중에 붙일 때 규약을 다시 안 고쳐도 됩니다.

> 💡 **콜 API와 워커의 권한을 나눈 이유(최소권한).** 콜 API는 큐에 **넣기만**, 워커는 **꺼내고 지우기만** 합니다. 한 역할에 `송수신`을 몰아넣으면 콜 API가 큐의 메시지를 지울 수 있게 되는데, 쓸 일이 없는 권한은 사고만 냅니다. 그래서 `worker-sa`를 별도로 둡니다.

> 💡 **`sqs:GetQueueUrl` 을 빼면 첫 요청에서 `AccessDenied` 로 죽습니다.** 앱은 큐 **이름**만 알고 **URL**은 모릅니다. `common/aws/sqs_adapter.py` 의 `queue_url` property 가 `send_message`·`receive_messages` 보다 **먼저** `get_queue_url` API 를 호출합니다. **KEDA 만 예외** — ScaledObject 에 `queueURL` 을 통째로 받으므로 `GetQueueUrl` 이 필요 없습니다.
>
> 🔧 **개선안(권장 · 앱팀·배포팀 합의 필요):** 배포팀이 ConfigMap 으로 `SQS_QUEUE_URL`(§7 `data.sqs_queue_url`)을 주입하면 어댑터가 `if self._queue_url: return` 으로 API 호출을 건너뜁니다. 그러면 **세 역할에서 `GetQueueUrl` 을 전부 뺄 수 있습니다.** 지금은 앱 코드가 큐 이름만 받으므로 권한을 부여합니다.

> 💡 **`predict` 에 SQS 읽기 권한이 붙은 이유.** `predict/app.py` 의 `/metrics` 와 dashboard·health 라우터가 큐 적체(`ApproximateNumberOfMessages`)를 조회합니다. 스케일 결정이 아니라 **관측용**이라 읽기만 주고 송신·수신·삭제는 주지 않습니다.

> 💡 **KEDA IRSA가 없으면 반응형 스케일링이 통째로, 그것도 조용히 죽습니다.** KEDA의 `aws-sqs-queue` 트리거는 **KEDA operator 자신이** SQS에 `GetQueueAttributes`를 호출해 큐 길이를 읽습니다. 이 역할이 없으면 큐가 아무리 쌓여도 파드가 안 늘고 에러도 안 납니다. manifests의 `TriggerAuthentication`(`hailcast-keda-auth`)이 이 역할 ARN을 참조합니다.
>
> ※ **ScaledObject 자체의 이름·네임스페이스는 §8** 에 있습니다(`hailcast` 네임스페이스의 `hailcast-worker-scaler`). 인프라가 만드는 리소스가 아니라 **배포팀이 만들고 predict 가 patch 하는 팀 간 계약**이라 그쪽에 둡니다. 값은 한 곳에만 둡니다.

> 💡 **애드온의 SA 이름은 우리 작명 규칙을 강요하지 않고 그 소프트웨어의 기본값을 씁니다.** `keda:keda-operator`는 KEDA Helm 차트 기본값입니다(`kube-system:karpenter`·`kube-system:aws-load-balancer-controller`도 같은 원칙). 억지로 바꾸면 Helm 옵션·공식 문서 예제·버전 업그레이드가 전부 어긋납니다.

> 💡 ⭐ **ScaledObject 를 patch 할 권한은 IRSA 가 아니라 K8s RBAC 입니다. 두 체계를 섞지 마십시오.**
> - **S3·SQS·DynamoDB 접근 = IRSA** (AWS 권한). 위 표가 그것입니다.
> - **ScaledObject `get`·`patch` = K8s RBAC** (클러스터 안 권한). IRSA 로는 절대 안 됩니다.
>
> **배포팀 할 일:** `hailcast:predict-sa` 에 `scaledobjects` 리소스의 `get`·`patch` 를 주는 **Role + RoleBinding** 을 만들어 주십시오. 앱 레포 `k8s/predict-rbac.yaml` 에 형태 예시가 있습니다(Role + RoleBinding · `verbs: ["get","patch"]`).
> ⚠️ **다만 그 예시가 묶는 SA 이름은 `hailcast-predict` 라 규약과 어긋나 있습니다.** 규약은 **`predict-sa`** 입니다(위 표). **manifests 는 앱 예시가 아니라 규약 이름을 기준으로 만드십시오.**
> IRSA 신뢰정책이 `system:serviceaccount:hailcast:predict-sa` 로 못을 박기 때문에, 파드가 다른 SA 로 뜨면 **AssumeRole 이 거부돼 '권한 없음'** 이 됩니다. 앱팀에는 SA 이름 정정을 요청해 두었습니다.
> ⚠️ **Role 은 네임스페이스 스코프입니다.** ScaledObject 가 predict 와 **같은 네임스페이스(`hailcast`)** 에 있어야 patch 가 됩니다(§8).
> 이게 없으면 IRSA 를 아무리 잘 붙여도 **선제 확장이 안 됩니다.** 그리고 IRSA 문제로 착각해 엉뚱한 데를 파게 됩니다.

# 6. 태그 규약 (기능 태그 + 비용 태그)
## 6-1. 자동 발견 태그 (기능용 — 빠지면 몇 시간 디버깅)
Karpenter와 ALB Controller는 '어느 서브넷에 자원을 만들까', '어느 SG를 노드에 달까'를 **태그를 보고 스스로 찾습니다.** 태그가 없으면 못 찾아 Ingress·노드가 안 뜨거나, 뜨더라도 조용히 오작동합니다.

| 태그 키 = 값 | 붙일 대상 | 누가 읽나 |
|---------------------------------------------|-----------------|-------------------------------|
| kubernetes.io/role/elb = 1                  | public 서브넷   | ALB Controller (외부 LB 위치) |
| kubernetes.io/role/internal-elb = 1         | private 서브넷  | 내부 LB 위치                  |
| karpenter.sh/discovery = hailcast-dev       | private 서브넷  | Karpenter (노드 띄울 **곳**)  |
| **karpenter.sh/discovery = hailcast-dev**   | **노드 SG** (`hailcast-dev-sg-eks-node`) | **Karpenter (노드에 달 SG)** |

> 💡 ⭐ **노드 SG 태그가 빠지면 앱이 DB에 못 붙습니다 — 그것도 에러 없이.** RDS는 5432를 '노드 SG를 단 놈'에게만 엽니다(§5-5). 그런데 정작 DB를 쓰는 파드(worker·call-api·predict)는 system 노드그룹이 아니라 **Karpenter가 띄우는 노드**에 삽니다. Karpenter는 EC2NodeClass의 `securityGroupSelectorTerms`로 SG를 **태그 검색**해 노드에 붙이므로, 이 태그가 없으면 그 노드는 노드 SG를 못 달고 → RDS가 문을 안 열어줍니다. 증상은 연결 타임아웃뿐이라 원인 추적이 어렵습니다.
>
> **서브넷과 SG의 태그 값은 같습니다(`hailcast-dev`).** Karpenter는 '노드를 띄울 곳(서브넷)'과 '노드에 달 SG'를 **둘 다** 이 태그로 찾으므로, 한쪽만 붙이면 안 됩니다.

> 💡 ⭐ **폐기 대상은 딱 하나 — 서브넷에 붙이던 `kubernetes.io/cluster/hailcast-dev-eks = shared` 입니다 (2026-07-14 · 레거시).**
> **서브넷에는 붙이지 않습니다.**
>
> 🚨 **오해 금지 — 같은 태그 키를 Karpenter 가 `= owned` 로 쓰고 있고, 그건 살아 있습니다.**
> Karpenter 가 **자기가 만든 EC2·런치템플릿·인스턴스프로파일**에 붙이는 `kubernetes.io/cluster/hailcast-dev-eks = owned` 는 **필수**입니다. IRSA 정책이 IAM Condition 으로 그 태그를 요구합니다
> (`modules/eks/policies/karpenter-node-lifecycle.json.tftpl:30,55,77,97,127` · `karpenter-iam-integration.json.tftpl:27,45,47,68` — `"aws:ResourceTag/kubernetes.io/cluster/${cluster_name}": "owned"`).
> **배포팀이 `EC2NodeClass` 의 `tags` 에서 이걸 빼면 `RunInstances`·`CreateFleet` 이 조건 불일치로 거부되어 Karpenter 가 노드를 한 대도 못 띄웁니다.**
> → 죽은 것은 **서브넷의 `= shared`**, 살아 있는 것은 **노드의 `= owned`** 입니다. **대상도 값도 다릅니다.**
>
> **폐기 근거 (AWS 공식 문서).**
> - **EKS**: "When a Kubernetes cluster that's version **1.18 and earlier** was created, Amazon EKS added the following tag to all of the subnets … **When you create a new Kubernetes cluster now, Amazon EKS doesn't add the tag to your subnets.** **Version 2.1.1 or earlier of the AWS Load Balancer Controller requires this tag. If you are using a newer version of the Load Balancer Controller, you can remove the tag without interrupting your services.**" ([EKS User Guide — VPC and subnet requirements](https://docs.aws.amazon.com/eks/latest/userguide/network-reqs.html))
> - **AWS Load Balancer Controller**: 서브넷 후보 선정은 **`kubernetes.io/role/elb`·`internal-elb`** 가 담당하고, cluster 태그는 **없어도 됩니다.** ([Subnet Discovery](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/deploy/subnet_discovery/))
> - **Karpenter**: SG 발견에 cluster 태그를 쓰면 LB Controller 와 충돌할 수 있으니 **`karpenter.sh/discovery` 를 쓰라**고 공식 권고합니다 — 우리 §6-1 표가 이미 그렇게 돼 있습니다. ([NodeClasses](https://karpenter.sh/docs/concepts/nodeclasses/))
>
> ⚠️ **"붙여도 무해"가 아닙니다. 안 붙이는 게 안전한 것입니다.** LB Controller 는 서브넷에 cluster 태그가 **있는데 클러스터 이름이 다르면 그 서브넷을 후보에서 탈락**시킵니다("Subnets with ineligible cluster tags will be filtered out"). 그래서 **틀리게 붙일 바엔 안 붙이는 게 낫습니다.**
>
> **우리 구성에 대입하면** — 클러스터는 **1.35**(EKS가 태그를 안 붙이는 버전), LB Controller 는 최신, 프라이빗 서브넷은 **AZ당 1개씩**이라 우선순위를 가릴 일도 없습니다. 발견을 실제로 담당하는 `role/elb`·`internal-elb` 는 이미 붙어 있습니다(`modules/network/main.tf:51`·`:69` 실측).
>
> ⚠️ **작업분담표의 `Y6`(서브넷 클러스터 태그)는 불필요한 일입니다.** 하지 않아도 됩니다. 전에 "❌ 누락"으로 잡혀 있던 것은 **누락이 아니라 필요 없는 항목**이었습니다.
>
> ※ `make check-contract`(ops)는 이 태그를 검사하지 않습니다(검증기 신규 작성분에 애초에 없음).

| ManagedBy   | terraform | 콘솔 수동 생성물과 구분 → 고아 리소스 추적 |

# 7. 모듈 output 계약 (모듈이 내보내는 값)
각 모듈의 outputs.tf가 곧 다른 모듈·다른 팀이 소비하는 계약입니다. 이 이름이 흔들리면 통합 때 연쇄로 무너집니다.

| 모듈 | output 이름 | 소비하는 쪽 |
|----------|-----------------------------------------------------------------------|---------------------------|
| network  | vpc_id / public_subnet_ids / private_subnet_ids / vpc_cidr            | eks · data     |
| eks      | cluster_name / cluster_endpoint / oidc_provider_arn / oidc_issuer_url / irsa_role_arns / **node_security_group_id** / **node_group_name** | 애드온 · manifests · data(§5-5) |
| storage  | model_bucket_name / **model_bucket_arn** / ecr_repository_urls        | predict(앱) · CI push · **eks(IRSA)** |
| data     | rds_endpoint / sqs_queue_url / sqs_queue_arn / secret_arn / **prediction_log_table_arn** / **karpenter_queue_arn** | 앱 · KEDA · **eks(IRSA)** |

> 💡 `node_security_group_id` 는 **data 모듈이 RDS 5432 ingress 에서 지목**하고(§5-5), **Karpenter EC2NodeClass 가 태그로 발견**합니다(§6-1). `sqs_queue_url` 은 배포팀이 ConfigMap 으로 앱에 주입하면 §5-3 의 `GetQueueUrl` 권한을 없앨 수 있습니다.

## 7-1. IRSA가 참조하는 값은 '이름'이 아니라 'ARN'입니다
IAM 정책은 리소스를 **ARN으로 지목**합니다. 이름(`model_bucket_name`)만으로는 정책을 쓸 수 없습니다. 그래서 §5-3의 IRSA 7종이 실제로 필요로 하는 ARN을 위 표에 명시했습니다.

| ARN output | 내보내는 모듈 | 이걸 쓰는 IRSA 역할 |
|---|---|---|
| `model_bucket_arn`         | storage | `irsa-predict` — 읽기 `models/*`+`predictions/*` · **쓰기는 `predictions/*` 만** (§5-3·§8) |
| `sqs_queue_arn`            | data    | `irsa-call-api` · `irsa-worker` · `irsa-keda` · `irsa-predict` |
| `prediction_log_table_arn` | data    | `irsa-predict`(오답노트 쓰기) |
| `karpenter_queue_arn`      | data    | `irsa-karpenter`(Spot 중단 경고 수신) |

## 7-2. output은 '모듈 최상단'에 있어야 계약이 성립합니다
§7이 말하는 "storage 모듈의 output"은 **`modules/storage/outputs.tf`(모듈 최상단)** 입니다.

서브모듈(`modules/storage/s3/`) 안에만 output이 있으면 **값이 모듈 내부에 갇혀** 다른 모듈이 `module.storage.model_bucket_arn`으로 꺼내 쓸 수 없습니다. 그리고 서브모듈은 **`module` 블록으로 불러야** Terraform 그래프에 들어옵니다 — 파일만 있고 호출이 없으면 `plan`에 `0 to add`가 뜨고 **리소스가 아예 만들어지지 않습니다.**

바로 따라 쓸 수 있게 두 단계를 적어 둡니다. (선례: `modules/data/main.tf`의 `module "rds"`)

```hcl
# ① modules/storage/main.tf — 서브모듈을 '호출'해야 그래프에 들어온다
module "s3" {
  source       = "./s3"
  project_name = var.project_name
  environment  = var.environment
  tags         = var.tags
}

# ② modules/storage/outputs.tf — 모듈 최상단에서 '재노출'해야 밖에서 쓸 수 있다
output "model_bucket_name" {
  description = "모델 아티팩트 S3 버킷 이름(랜덤 접미사 포함). predict 앱이 참조."
  value       = module.s3.model_bucket_name
}

output "model_bucket_arn" {
  description = "모델·예측 JSON S3 버킷 ARN. eks 모듈의 IRSA 정책이 Resource 로 지목."
  value       = module.s3.model_bucket_arn
}
```

> 💡 `modules/data`의 `sqs`·DynamoDB·Karpenter 중단 큐도 동일합니다 — `modules/data/main.tf`에서 호출하고, `modules/data/outputs.tf`에서 `sqs_queue_arn`·`prediction_log_table_arn`·`karpenter_queue_arn` 이름으로 재노출합니다. **서브모듈 내부 output 이름이 달라도 괜찮습니다. 밖으로 나오는 이름만 이 표와 같으면 계약은 지켜집니다.**

# 8. 팀 전체 공유 계약 (인프라 → 앱·ML·배포)
인프라가 만들고 **다른 팀이 코드에 그대로 참조**하는 이름들입니다. 이것이 어긋나면 다른 팀이 병렬로 나가지 못합니다. 착수 전 반드시 못 박습니다.

| 계약 항목 | 확정 값 | 만드는 쪽 → 쓰는 쪽 | 어긋나면 |
|------------------|------------------------------------------------------|-------------------------|------------------------------|
| 예측 지표 이름   | **predicted_taxi_demand** · **float** (타입만 개정)   | 예측 → S3 JSON → scaler → ScaledObject | 선제 스케일 조용히 불발 |
| K8s 네임스페이스 | 앱 = hailcast · KEDA = keda                          | 이름=인프라 확정 · 생성=배포팀(ArgoCD) → 전원 | 배포 위치 혼선 · IRSA '권한 없음' |
| KEDA ScaledObject | **`hailcast` 네임스페이스**의 **`hailcast-worker-scaler`** | 이름=인프라 확정 · 생성=배포팀 → **scaler 가 patch** | 선제 확장 불발 |
| **`KEDA_ENABLED`** | **`true`** (ConfigMap 으로 주입) | 배포팀 → predict | **dry-run 으로 조용히 돈다** (아래 주석) |
| **predict `replicas`** | **`1` 고정** | 배포팀 → predict | 스케줄러 중복 실행 |
| ECR 이미지 태그  | 커밋 SHA (\$GITHUB_SHA)                              | 앱 CI → manifests       | '지금 뭐가 도는지' 추적 불가 |
| SQS 콜 큐        | hailcast-dev-call-queue                              | 인프라 → 앱·KEDA        | 안전망 불발                  |
| 모델 S3 경로     | s3://hailcast-dev-model-artifacts-…/**models/latest/model.txt** + **metadata.json** | ML → S3 → predict | 모델 로드 실패 |
| IRSA 역할 ARN    | §5-3 참조                                            | 인프라 → manifests      | '권한 없음' 폭탄             |

> 💡 ⭐ **`KEDA_ENABLED` 를 안 켜면 선제 스케일링이 통째로, 그것도 조용히 죽습니다 (2026-07-13 등재).**
> 앱 기본값이 **`false`** 입니다(`predict/config.py`). false 면 predict 가 **InMemory dry-run 어댑터**를 물고 ScaledObject 를 **아예 건드리지 않습니다.** 그런데 로그에는 `replica changed 1 -> 3` 이 정상처럼 찍힙니다.
> → **배포팀이 ConfigMap 에 `KEDA_ENABLED: "true"` 를 넣어야 합니다.** 앱 레포 `k8s/` 에 예시가 있습니다.
> ※ 켜졌는지 확인하는 법: `GET /scaling/status` 응답과 대시보드에 `keda_enabled` 값이 그대로 노출됩니다. 시연 전에 눈으로 한 번 보십시오.

> 💡 ⭐ **predict 는 `replicas: 1` 로 고정해야 합니다 (2026-07-13 등재).**
> 결정 1(predict 내장)이라 **예측 스케줄러와 스케일 스케줄러가 predict 파드 안에 삽니다.** 파드가 2개 뜨면 **같은 예측을 두 번 만들어 S3 에 덮어쓰고, ScaledObject 도 두 번 patch** 합니다. 앱 `k8s/predict-deployment.yaml` 에도 "반드시 1" 이라 적혀 있습니다.
> ⚠️ **predict 를 HPA·KEDA 로 스케일하지 마십시오.** 스케일 대상은 **worker** 입니다.

> 💡 ⭐ **ScaledObject 는 이름과 네임스페이스가 '한 쌍'이라야 계약이 성립합니다 (2026-07-13 등재).**
> 선제 확장은 결국 **scaler 가 ScaledObject 의 `minReplicaCount` 를 patch** 해서 일어납니다. patch 는 **네임스페이스와 이름 둘 다로** 대상을 지정합니다(`predict/adapters/kubernetes_keda_adapter.py:53-55` — `patch_namespaced_custom_object(..., self._namespace, _PLURAL, self._name, ...)`). **둘 중 하나만 어긋나도 대상을 못 찾습니다.**
>
> | | 값 | 실측 |
> |---|---|---|
> | 이름 | `hailcast-worker-scaler` | `predict/config.py:50` · 앱 `k8s/worker-scaledobject.yaml:6` |
> | 네임스페이스 | `hailcast` (= 앱 네임스페이스) | 앱 **기본값이 `default`** 라 어긋나 있음(`predict/config.py:49`) |
>
> **`KEDA_NAMESPACE` 는 환경변수라 코드를 안 고쳐도 됩니다.** 배포팀이 ConfigMap 에 `KEDA_NAMESPACE: hailcast` 한 줄을 넣으면 끝입니다(앱 `README.md` 환경변수 표 참조). 앱 기본값을 함께 고치면 더 안전합니다.
>
> **인프라는 이름만 확정합니다. 실제 생성은 배포팀(ArgoCD)** 입니다. 그래서 §5-3(인프라가 만드는 eks 리소스 표)이 아니라 여기(팀 간 계약)에 둡니다. **patch 하는 주체는 결정 1(방식 B 수행 주체)에 달려 있으므로 여기서는 `scaler` 라고만 씁니다.**
>
> ⚠️ **어긋나면 파드가 안 늡니다. 다만 조용하지는 않습니다.** patch 가 실패하면 `KubernetesError` → `ScalingError` 로 올라가고 `patch_failed` 로그가 남습니다(`kubernetes_keda_adapter.py:67-70` · `scaler_service.py`). **로그를 안 보면 "예측은 오르는데 파드가 그대로"인 그림만 보입니다.** 시연 전에 이 로그를 한 번 확인하세요.

> 💡 ⭐ **모델 S3 경로 개정 (2026-07-13) — 규약이 틀렸고 앱 코드가 옳았습니다.**
> 옛 규약은 `latest_model.pkl` 한 파일이었으나, **앱은 pickle을 쓰지 않습니다.** LightGBM 네이티브 포맷(`model.txt`)입니다.
> **코드가 옳은 이유가 둘입니다.** ① pickle은 역직렬화 시 **임의 코드가 실행**될 수 있습니다. 모델 파일은 S3에서 내려받아 그대로 로드하므로 위험합니다. ② pickle은 라이브러리 버전이 바뀌면 **조용히 깨집니다.** 네이티브 포맷은 그렇지 않습니다.
>
> **실제 버킷 구조** (`ml/train.py:90-92` · `predict/ml_runtime/model_loader.py:24-30` · `predict/services/prediction_service.py:147-150` 실측)
> ```
> s3://hailcast-dev-model-artifacts-<랜덤>/
> ├── models/                        ← 학습(ml/train.py)이 쓰고, 예측이 읽는다
> │   ├── latest/                        예측은 항상 여기만 읽는다
> │   │   ├── model.txt                  (LightGBM 네이티브)
> │   │   └── metadata.json              (version · cv_mae …)
> │   └── <version>/                     학습할 때마다 버전 사본을 함께 남긴다
> │       ├── model.txt
> │       └── metadata.json
> └── predictions/                   ← 예측이 쓰고, scaler 가 읽는다
>     ├── latest.json                    scaler 가 읽는 것은 이 파일 하나
>     └── history/
>         └── <YYYYmmdd-HHMMSS>.json     이력 (기본 활성 · `prediction_keep_history_in_s3`)
> ```
> **`metadata.json` 도 계약입니다.** 예측 쪽은 **`metadata.json` 을 매 실행마다 내려받아 `version` 을 비교**하고, 버전이 바뀌었거나 파드가 막 뜬 경우에만 `model.txt` 를 받습니다(`model_loader.py:24-29`). 이 파일이 없거나 이름이 다르면 **모델 갱신이 조용히 멈춥니다.** 헬스체크도 이 파일을 읽습니다(`predict/services/health_service.py`).
>
> **IRSA 를 경로별로 자를 수 있습니다 (프리픽스가 갈려 있으니).** 정책이 지목할 문자열은 아래와 같습니다.
>
> | 대상 | 권한 | Resource |
> |---|---|---|
> | **읽기** — 모델 + 예측 JSON | `s3:GetObject` | `…/models/*` **그리고** `…/predictions/*` |
> | **쓰기** — 예측 결과만 | `s3:PutObject` | `…/predictions/*` **(여기만)** |
> | 키 목록 조회 | `s3:ListBucket` | **버킷 ARN 자체** (`/*` 를 붙이지 않는다) |
> | 모델 쓰기 (`ml/train.py`) | — | **클러스터 밖에서 실행 → IRSA 대상 아님** (안에서 Job 으로 돌리면 역할 추가) |
>
> ⚠️ ⭐ **읽기와 쓰기를 다르게 자르는 게 이 정책의 핵심입니다. 읽기는 두 프리픽스 다, 쓰기는 `predictions/` 만.**
>
> - **읽기를 `models/*` 로만 자르면 scaler 가 죽습니다.** predict 는 모델만 읽는 게 아니라 **`predictions/latest.json` 도 읽습니다**(`prediction_reader.py:24,28` → `s3:GetObject`). 그걸 못 읽으면 스케일 결정 자체가 안 됩니다.
> - **쓰기를 `predictions/latest.json` 하나로 좁혀도 깨집니다.** 이력(`predictions/history/*.json`)이 함께 올라갑니다(`prediction_service.py:149-150` · 기본 활성). **프리픽스 전체**를 줘야 합니다.
> - **쓰기에 버킷 전체를 주면 안 됩니다.** 예측을 쓰는 쪽이 `models/latest/model.txt` 를 덮어써 **학습된 모델을 통째로 날릴 수 있습니다.**
> - `s3:ListBucket` 은 대상이 **버킷 자체**라 `/*` 를 붙이지 않습니다. 붙이면 목록 조회가 안 됩니다.

> 💡 **네임스페이스의 실제 생성은 배포팀(ArgoCD)이 YAML로 선언합니다.** GitOps 원칙상 "클러스터 안 상태는 전부 Git에 선언"이므로, 인프라가 `kubectl`로 직접 만들면 ArgoCD가 모르는 리소스가 되어 drift가 납니다. **인프라는 이름만 확정**하고, IRSA가 `hailcast:predict-sa` 형태로 이 이름에 묶이니(§5-3) 오타 시 '권한 없음'으로 이어집니다.
>
> **앱 네임스페이스 = `hailcast`** (predict·call-api·worker·weather-cron·frontend·simulator). **KEDA 네임스페이스 = `keda`**, SA = `keda-operator` — 배포팀 요청으로 인프라가 확정한 값입니다(Helm 차트 기본값 준수). Karpenter·ALB Controller는 관례대로 `kube-system`입니다.

> 💡 ⭐ **예측 지표 이름이 이 프로젝트의 심장입니다 (2026-07-13 개정 — 규약을 코드에 맞춤).**
> 예측이 **`predicted_taxi_demand`** 키로 예측 JSON을 S3에 쓰고, scaler 가 **정확히 이 키를 읽어** ScaledObject의 `minReplicaCount`를 미리 끌어올립니다. 키 이름이 한 글자만 달라도 선제 확장이 **조용히** 불발됩니다.
>
> **이름은 규약값 그대로 두고 타입만 고칩니다 (정수 → float).**
> 규약이 SSOT 이고 앱이 따라옵니다. 앱 코드에는 이 이름이 없었고 실제 키가 `total_predicted_demand` 였는데, **앱팀(창원·재혁)이 규약 이름으로 맞추기로 확정**했습니다(2026-07-13). 타입은 **float 로 확정** — KEDA 가 쓰는 값의 성격상 float 가 맞다는 앱팀 판단입니다.
> 값의 의미는 **첫 시간창(60분)의 전 구역 합계**입니다(`common/models/prediction.py`).
>
> **float 는 문제가 되지 않습니다.** 예측값이 파드 수로 '변환'되지 않기 때문입니다. `predict/config.py:40` 의 임계값 규칙표(`scaling_rules = "20:1,50:2,100:3,300:5,500:10"`)로 **구간을 찾고**, 파드 수는 그 표에서 이미 정수로 나옵니다(`scaling_decision_engine.py:33`). 3.7 이든 3.2 든 똑같이 "20 미만 → 1개" 입니다. 소수점이 잘려 파드가 모자라는 일은 없습니다.
>
> ⚠️ **KEDA 자신은 이 지표를 읽지 않습니다.** 방식 B에서 KEDA 트리거는 **SQS 큐 길이(`GetQueueAttributes`)** 하나뿐입니다(§5-3 `irsa-keda`). 예측은 트리거로 들어가는 게 아니라, scaler 가 **'자'(minReplicaCount)를 미리 바꿔두는** 방식으로 반영됩니다.

> **예측 → 스케일 경로 = 방식 B (S3 JSON) 확정.** 예측 Pod의 Prometheus 노출 방식(A)은 폐기.
> **수행 주체 = predict 내장** (결정 1 · 팀 잠정 전제). 별도 CronJob 2개가 아니라 **predict 프로세스 안의 스케줄러 2개**가 그 일을 합니다(`predict/dependencies.py:49-50`·`100-101`). 앱 dev 에 그렇게 머지돼 있습니다.
>
> | | 무엇을 | 주기 (코드 기본값) |
> |---|---|---|
> | `ForecastScheduler` | 예측 → JSON → S3 `predictions/latest.json` | **30분** (`prediction_interval_seconds = 1800`) |
> | `ScalingScheduler` | JSON 읽어 ScaledObject patch | **60초** (`scaling_interval_seconds = 60`) |
> | `weather-cron` | Open-Meteo 수집 (별도 서비스) | **10분** (`weather_interval_seconds = 600`) |
>
> ※ **`weather-cron` 은 기본 CMD 가 루프 모드라 Deployment 로 뜹니다.** CronJob 으로 돌리려면 `--once` 로 command 를 덮어써야 합니다(`weather-cron/fetch.py`). 배포팀이 어느 쪽으로 할지 정해 주십시오.
>
> ⚠️ ⭐ **예측 주기를 1시간보다 길게 잡으면 선제 스케일링이 대부분 멈춥니다.**
> `prediction_max_age_seconds = 3600`(1시간)이라, **1시간보다 오래된 예측으로는 스케일하지 않습니다**(`scaler_service.py:102-108`). 예측을 **4시간마다** 돌리면 **4시간 중 3시간은 예측이 만료돼 스케일링이 통째로 건너뛰어집니다.** 로그에 `prediction too old` 만 남고 파드는 안 늡니다.
> **여러 시간창을 미리 만들어 둬도 소용없습니다.** scaler 는 **첫 창의 스칼라 값 하나만** 읽고 `predictions[]` 는 보지 않으며, 무엇보다 신선도 게이트가 값을 읽기 **전에** 걸립니다.
> → **예측 주기를 늘리려면 `PREDICTION_MAX_AGE_SECONDS` 도 함께 늘려야 합니다. 둘은 한 쌍입니다.**
>
> - 예측 JSON 경로: `s3://hailcast-dev-model-artifacts-<랜덤>/predictions/latest.json` (확정) + `predictions/history/<타임스탬프>.json` 이력
> - **예측 지표 단위: 60분 시간창의 전 구역 합계 · float** (`prediction_window_minutes = 60`)
>   ⚠️ **`scaling_rules` 임계값(20·50·100·300·500)은 이 "60분 창 합계" 기준으로 읽어야 합니다.** 30분으로 착각하면 임계값을 절반으로 잘못 잡습니다.
