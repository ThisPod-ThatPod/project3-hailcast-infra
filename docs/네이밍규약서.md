# hailcast 인프라 레포 — 네이밍 규약서

> **이름은 곧 계약이다.** 여기 정한 문자열을 앱·ML·배포팀이 코드에 그대로 참조한다.
> 이 문서가 모든 리소스 이름의 **단일 진실원천(Single Source of Truth)**이다. 이름을 바꿔야 하면 **이 문서를 먼저 고치고** 팀에 공유한 뒤 코드를 바꾼다.
>
> 대상 레포: `project3-hailcast-infra` · 담당: 이미선, 유현상 · 리전: `ap-northeast-2`(서울)

---

# 1. 네이밍 대원칙
## 1-1. 이름 공식

거의 모든 AWS 리소스 이름은 아래 한 공식으로 만들어집니다.

```
<project_name>-<environment>-<리소스종류>[-<식별자>]
```

예) `hailcast-dev-vpc` · `hailcast-dev-subnet-public-2a` · `hailcast-dev-rds-postgres`

## 1-2. 문자 규칙 (지키지 않으면 apply가 실패)
| 대상 | 규칙 | 이유 |
|-------------------|-----------------------------------------|------------------------------------------------|
| Terraform 변수 | snake_case (소문자+밑줄) | HCL 관례  |
| AWS 리소스 이름   | kebab-case (소문자+하이픈)              | 대부분 AWS 리소스가 대문자·밑줄 불가           |
| S3 버킷 이름      | 소문자+하이픈, 밑줄 금지, **전역 유일** | 전 세계에서 하나뿐이어야 함 → 랜덤 접미사 필수 |
| 예측 지표(메트릭) | snake_case                              | Prometheus 관례 · KEDA 쿼리와 정확히 일치      |

# 3. tfstate 원격 백엔드 (0순위 · Terraform 부트스트랩)
팀 7명이 같은 상태 파일(tfstate)을 공유해야 협업이 됩니다. 이 버킷은 Terraform이 스스로 못 만드는 '닭-달걀' 문제라 **버킷 생성 단계만 backend 없이(로컬 상태로) 부트스트랩** 합니다. 만든 뒤 정확한 문자열을 backend.tf에 박습니다.

**상태 잠금은 S3 네이티브 락(use_lockfile)을 쓴다. 별도 DynamoDB 락 테이블은 만들지 않는다.** Terraform 1.11부터 `use_lockfile`이 정식 지원되면서, DynamoDB 락 테이블(과거 방식)은 deprecated로 향후 제거 예정입니다. 리소스가 하나 줄어 더 단순하고 비용도 아낍니다. (전제: 팀 전원 Terraform 1.11+ 사용 → versions.tf에 고정)

| backend.tf 항목 | 확정 값 | 설명 |
|---------------------|---------------------------|-------------------------------------------------------------|
| bucket              | hailcast-dev-tfstate-9dcb | 상태 저장+잠금 전용 버킷 (뒤 4자리는 실제 생성 값)          |
| key                 | dev/terraform.tfstate     | 상태 파일 경로 (환경 하나라 경로도 하나)                    |
| region              | ap-northeast-2            | 버킷 리전                                                   |
| use_lockfile        | true                      | S3 자체 잠금으로 동시 apply 방지 (DynamoDB 락 테이블 대체)  |
| encrypt             | true                      | 상태엔 시크릿이 평문으로 들어가므로 암호화 필수             |

> ⚠️ **DynamoDB 락 테이블 금지**: 전에는 `dynamodb_table` 방식을 썼으나, 3차 프로젝트에서는 `use_lockfile`로 대체한다. 코드에 `dynamodb_table` 인자가 있으면 제거 대상이다.
> 💡 버킷을 만든 인프라 담당이 실제 버킷 이름(랜덤 접미사 포함)을 확인해 backend.tf에 반영한다. (use_lockfile은 Terraform 1.11+ 필요)
> 출처: HashiCorp 공식 S3 backend 문서 — https://developer.hashicorp.com/terraform/language/backend/s3
> ("DynamoDB-based locking is deprecated and will be removed in a future minor version")

## 5-3. eks 모듈 — 클러스터 · 노드 · OIDC · IRSA
| 리소스 | 이름 / 값 | 비고 |
|------------------------|----------------------------|------------------------------------------------|

| System 노드그룹        | hailcast-dev-eks-system-ng | 관리형 · CoreDNS·Karpenter·KEDA·ArgoCD 호스팅  |
| Karpenter NodePool     | default                    | 앱 노드는 전부 Karpenter가 0부터 공급 [설계]   |
| Karpenter EC2NodeClass | default                    | 노드 AMI·서브넷·SG 템플릿                      |
| OIDC Provider          | (EKS가 자동 생성)          | IRSA 전제 · enable_irsa=true 한 줄             |

> ⚠️ **클러스터 이름은 `hailcast-dev-eks` 하나로 통일한다.** 서브넷 태그·큐 이름 등에서 `hailcast-dev`로 축약해 부르면 클러스터명과 문자가 어긋나 자동 발견이 조용히 실패한다. 아래처럼 locals 한 곳에서 파생시켜 오타·분열을 원천 차단한다.
> ⚠️ **버전 근거**: EKS 1.31은 2025-11-26 표준 지원 종료 → 확장 지원(요금 약 6배, 시간당 ≈$0.10→$0.60) 구간이므로 사용 금지. 1.33은 표준 지원 + Karpenter 1.5+ 지원. FinOps가 주제인 프로젝트에서 버전 방치로 비용이 새면 안 된다. (착수 시 EKS 버전 캘린더 재확인)
> 출처: AWS EKS 버전 라이프사이클 — https://docs.aws.amazon.com/eks/latest/userguide/kubernetes-versions.html

**이름의 단일 진실원천 (locals 파생)** — 클러스터명과 '발견용 라벨'은 다른 물건이다. 헷갈리지 않게 분리한다.

```hcl
# eks 모듈 (또는 envs/dev)
locals {
  cluster_name  = "${var.project_name}-${var.environment}-eks"  # hailcast-dev-eks (실제 클러스터명)
  discovery_key = "${var.project_name}-${var.environment}"      # hailcast-dev (Karpenter/서브넷이 서로를 찾는 '라벨')
  # ↑ discovery_key 값 자체는 임의여도 됨. 단, 서브넷 태그와 EC2NodeClass selector가 서로 같기만 하면 된다.
}
```

**IRSA 역할** — 파드마다 발급하는 '제한된 사원증'. 신뢰관계에 클러스터 OIDC provider ARN이 박히므로 **eks 모듈에 함께 둔다**(별도 security 모듈로 빼면 OIDC 의존 때문에 생성 순서가 꼬임 = chicken-egg). 아래 역할명·SA는 manifests의 serviceaccount.yaml과 맺는 계약이다.

| IRSA 역할명 | 연결 SA (네임스페이스:이름) | 권한 범위 |
|---|---|---|
| `hailcast-dev-irsa-predict` | `hailcast:predict-sa` | S3 모델 읽기 (상시 예측 서비스 파드) |
| `hailcast-dev-irsa-forecast` | `hailcast:forecast-sa` | S3 model-artifacts 읽기·쓰기 (배치 크론잡) |
| `hailcast-dev-irsa-call-api` | `hailcast:call-api-sa` | SQS 콜 큐 송수신 |
| `hailcast-dev-irsa-monitoring` | `monitoring:monitoring-sa` | CloudWatch 읽기 |
| `hailcast-dev-irsa-karpenter` | `kube-system:karpenter` | EC2 관리 + 중단 큐 수신 |
| `hailcast-dev-irsa-lbctrl` | `kube-system:aws-load-balancer-controller` | ALB 생성·관리 |

> 💡 **predict vs forecast는 다른 워크로드다.** predict는 상시 예측 서비스 파드(S3 모델 읽기만), forecast는 주기 배치 크론잡(예측 JSON을 S3에 쓰므로 읽기·쓰기). 권한이 다르므로 역할도 분리한다.
> 💡 **keda-scaler-updater-cronjob은 별도 IRSA 역할을 두지 않는다.** S3 읽기용 IRSA(forecast 역할 공유 또는 최소 읽기 역할) + K8s RBAC(`scaledobjects.keda.sh`에 `get`·`patch`) 조합으로 동작한다. ScaledObject는 쿠버네티스 리소스라 IRSA(AWS 권한)가 아닌 RBAC(K8s 권한) 소관이다. 두 체계를 섞지 말 것. (상세: README §7)

> 💡 예측 결과·시계열은 S3(예측 JSON)와 Prometheus로 커버한다. 별도 DynamoDB·Redis 계층은 두지 않는다(단일 환경·FinOps 관점 — 상시 과금 저장소 불필요).

**Secrets · 설정** — DB 비번은 Secrets Manager, 비밀 아닌 설정은 무료 Parameter Store. RDS와 함께 **data 모듈에 둔다**(클러스터와 무관).

| Secrets / 설정 | 이름 / 값 | 비고 |
|---|---|---|
| Secrets Manager (DB 비번) | `hailcast-dev-secret-rds` | random_password 자동생성 → 보관 |
| Parameter Store (DB 주소 등) | `/hailcast/dev/rds/endpoint` | 비밀 아닌 설정 → 무료 Parameter Store |

> 💡 진짜 비밀번호만 Secrets Manager(유료), DB 주소 같은 '비밀 아닌 설정'은 무료 Parameter Store로 나눠 담으면 비용이 줄어든다.

# 6. 태그 규약 (기능 태그 + 비용 태그)
## 6-1. 서브넷 자동 발견 태그 (기능용 — 빠지면 몇 시간 디버깅)
Karpenter와 ALB Controller는 '어느 서브넷에 자원을 만들까'를 **태그를 보고 스스로 찾습니다.** 태그가 없거나 클러스터명이 어긋나면 못 찾아 Ingress·노드가 안 뜹니다.

| 태그 키 = 값 | 붙일 서브넷 | 누가 읽나 |
|-------------------------------------------------|-----------------|-----------------------------------|
| kubernetes.io/role/elb = 1                      | public          | ALB Controller (외부 LB 위치)     |
| kubernetes.io/role/internal-elb = 1             | private         | 내부 LB 위치                      |
| karpenter.sh/discovery = hailcast-dev           | private         | Karpenter (노드 띄울 곳 · 임의 라벨) |
| kubernetes.io/cluster/hailcast-dev-eks = shared | private         | EKS 소유 서브넷 표시 (★실제 클러스터명) |

> ⚠️ **`kubernetes.io/cluster/` 뒤는 반드시 실제 클러스터명(`hailcast-dev-eks`)이어야 한다.** 이 태그는 클러스터명과 문자 그대로 일치해야 EKS가 서브넷을 자기 것으로 인식한다. 어긋나면 존재하지 않는 클러스터를 가리키는 '고아 태그'가 되어 자동 발견이 조용히 실패한다.
> 💡 `karpenter.sh/discovery` 값(`hailcast-dev`)은 임의 라벨이라 클러스터명과 달라도 된다 — 서브넷 태그와 EC2NodeClass selector만 서로 같으면 된다. 이 둘(클러스터명 vs 발견용 라벨)을 혼동하지 말 것.

## 6-2. 공통 비용 태그 (default_tags — OpenCost·Budgets 근거)
OpenCost와 Budgets는 '이 비용이 누구 것이냐'를 태그로 판단합니다. providers.tf에 한 번 선언하면 모든 리소스에 자동으로 붙습니다.

| 태그 키 | 값 | 용도 |
|-------------|-----------|--------------------------------------------|
| Project     | hailcast  | 프로젝트 단위 비용 집계                    |
| Environment | dev       | 환경 구분                                  |
| ManagedBy   | terraform | 콘솔 수동 생성물과 구분 → 고아 리소스 추적 |

# 7. 모듈 output 계약 (모듈이 내보내는 값)
각 모듈의 outputs.tf가 곧 다른 모듈·다른 팀이 소비하는 계약입니다. 이 이름이 흔들리면 통합 때 연쇄로 무너집니다.

| 모듈 | output 이름 | 소비하는 쪽 |
|----------|-----------------------------------------------------------------------|---------------------------|
| network  | vpc_id / public_subnet_ids / private_subnet_ids / vpc_cidr            | eks · data     |
| eks      | cluster_name / cluster_endpoint / oidc_provider_arn / oidc_issuer_url / irsa_role_arns | 애드온 · manifests |
| storage  | model_bucket_name / ecr_repository_urls                               | predict(앱) · CI push     |
| data     | rds_endpoint / sqs_queue_url / sqs_queue_arn / secret_arn         | 앱 · KEDA          |

# 8. 팀 전체 공유 계약 (인프라 → 앱·ML·배포)
인프라가 만들고 **다른 팀이 코드에 그대로 참조**하는 이름들입니다. 이것이 어긋나면 다른 팀이 병렬로 나가지 못합니다. 착수 전 반드시 못 박습니다.

| 계약 항목 | 확정 값 | 만드는 쪽 → 쓰는 쪽 | 어긋나면 |
|------------------|------------------------------------------------------|-------------------------|------------------------------|
| 예측 지표 이름   | predicted_taxi_demand                                | 앱 → KEDA·Prometheus    | 선제 스케일 조용히 불발      |
| K8s 네임스페이스 | 앱 워크로드=hailcast · 시스템=kube-system/monitoring | 인프라 → 전원           | 배포 위치 혼선               |
| ECR 이미지 태그  | 커밋 SHA (`\$GITHUB_SHA`)                            | 앱 CI → manifests       | '지금 뭐가 도는지' 추적 불가 |
| SQS 콜 큐        | hailcast-dev-call-queue                              | 인프라 → 앱·KEDA        | 안전망 불발                  |
| 모델 S3 경로     | s3://hailcast-dev-model-artifacts-…/latest_model.pkl | 인프라 → predict        | 모델 로드 실패               |
| IRSA 역할 ARN    | §5-3 참조                                            | 인프라 → manifests      | '권한 없음' 폭탄             |

> 💡 K8s 네임스페이스는 "전원 hailcast"가 아니다. **앱 워크로드는 `hailcast`**, Karpenter·ALB Controller 등 **시스템 컴포넌트는 `kube-system`**, 모니터링은 `monitoring` 네임스페이스에 산다(§5-3 IRSA 표와 일치).
> 💡 예측 지표는 ML(생산자)과 인프라·KEDA(소비자) 사이의 계약이다. **값의 의미·단위는 ML이 정하고, 이름 문자열과 형식은 양쪽이 합의**해 한 줄로 확정한다. (예: 이름 `predicted_taxi_demand`, 의미 '분당 예상 호출 건수', 형식 정수)
