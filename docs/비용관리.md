# hailcast 공용 AWS 계정 — 비용관리 런북 (FinOps)

> 이 프로젝트는 **예측형 오토스케일링 + FinOps**가 주제다. 비용을 "측정"하지 못하면
> 절감 효과도 증명하지 못한다. 이 문서는 공용 계정에서 **폭탄 비용을 막고**,
> **누가 얼마 썼는지 정확히 집계**하기 위한 실전 절차다.
>
> 관련: `docs/네이밍규약서.md` §6(태그 규약) · 담당 조율 필요(결제 권한은 계정 주인)

---

## 0. 대원칙 3줄
1. **작성(코드)엔 계정이 필요 없다.** `fmt`·`validate`는 자격증명 0. 계정이 필요한 건 `plan`·`apply`·`destroy`뿐 → CI(OIDC) 또는 통합테스트 담당이 수행.
2. **안 써도 과금되는 게 있다.** EKS 컨트롤플레인·NAT·RDS는 켜만 놔도 시간당 돈이 나간다 → 데모 안 할 땐 내린다.
3. **태그 없으면 비용 집계가 샌다.** 특히 K8s가 만든 자원(노드·LB)은 자동 태그가 안 붙는다(§3).

---

## 1. 제일 먼저 할 일 — Budgets 월 예산 + 알림 (약 5분)
"모르는 새 폭탄"을 막는 **1순위 안전망**. 콘솔 → Billing → Budgets.

- **월 예산** 설정 (예: `$50` — 데모 규모에 맞게).
- **알림 임계치**: 실제 사용 80%, **예상 사용 100%** 두 개 걸고 → **이메일 경보**.
- ⚠️ Budgets/결제 화면은 **root 또는 billing 권한**이 필요. 없으면 계정 주인에게 요청.

> 이 하나만 걸어도 위험의 대부분이 사라진다. 다른 건 못 하더라도 이건 한다.

## 2. 비용 가시화 — Cost Explorer를 태그로 보기
우리는 `providers.tf`의 `default_tags`로 모든 Terraform 자원에 태그를 자동 부착한다.
- Cost Explorer → **그룹화 기준 = 태그 `Project`** → "hailcast가 총 얼마" 즉시 확인.
- **Cost Anomaly Detection**(무료) 켜두면 급증을 자동 감지해 알려준다.

## 3. ⭐ 태그 커버리지 — 자동 vs 새는 구멍

### 3-1. 원리
**`default_tags`는 "infra의 Terraform이 직접 만든 자원"에만** 붙는다. 그 밖(런타임에 K8s 컨트롤러가 만들거나, AWS 서비스가 대신 만든 것)엔 안 붙는다.

> 비유: `default_tags`는 우리 공장(Terraform) 출고품에 자동으로 찍히는 바코드다.
> 나중에 로봇(K8s 컨트롤러)이 공장 밖에서 따로 찍어낸 물건엔 그 바코드가 없다 — 하필 그게 제일 비싼 노드·LB다.

### 3-2. 앞으로 태그가 안 붙어 나오는 것들
| 부류 | 자원 | 왜 안 붙나 | 소관 |
|---|---|---|---|
| **A. infra가 부모는 만들지만 자식이 샘** | **EKS 클러스터 보안그룹** | 클러스터 생성 시 **EKS가 자동 생성** → `default_tags` 대상 아님 | 인프라 |
| | **System 관리형 노드그룹의 EC2 인스턴스** | 노드그룹 태그가 **인스턴스까지 전파 안 됨**(ASG 경유). 인스턴스에 붙이려면 **launch template의 `tag_specifications`** 필요 | 인프라 |
| **B. K8s가 런타임에 통째로 만듦** | Karpenter **노드(EC2)**·런치템플릿 | Terraform이 아니라 Karpenter가 생성 | 배포(manifests)팀 |
| | ALB Controller의 **LB·타깃그룹·리스너·SG** | 런타임 생성 | 배포팀 |
| | PVC의 **EBS 볼륨** | EBS CSI 드라이버가 생성 | 배포팀 |
| **C. 기타** | 태그 미지원 리소스, **콘솔 수동 생성물** | 태그 불가/사람이 안 붙임 | 전원 |

> 🔴 **하필 제일 비싼 자원(노드·LB)이 A·B에 속한다.** 태그가 없으면 절감 측정에서 가장 큰 비용이 빠져 FinOps가 통째로 어긋난다.

### 3-3. 현재 상태 (2026-07-25 실측)
클러스터와 애드온이 배포돼 §3-2의 A·B 자원이 실재한다. 비용 태그 세 개(Project·Environment·ManagedBy) 기준으로 본 커버리지다.

**비용 할당 태그 3종을 2026-07-25 활성화했다.** 그전 사용분은 태그별 집계가 전액 미귀속이고, CUR의 `resourceTags` 열도 다음 배달분부터 생긴다. OpenCost Level 2가 태그로 쪼개는 것도 그 뒤부터다. 활성화는 Billing 콘솔이라 계정 주인이 한다(§1과 같다). 아래 표가 집계되는 범위다.

| 자원 | 비용 태그 | 붙이는 곳 |
|---|---|---|
| System 노드그룹 EC2·EBS | 셋 다 | infra `modules/eks/nodegroup.tf:79-96` (launch template `tag_specifications`) |
| Karpenter 노드 EC2·EBS | 셋 다 | manifests `addons/karpenter/ec2nodeclass.yaml:17-21` |
| ALB·타깃그룹·리스너·리스너룰 | Project·Environment만 · **ManagedBy 없음** | manifests `apps/call-api/ingress.yaml:25` · `apps/predict/ingress.yaml:16` · `apps/frontend/ingress.yaml:20`의 `alb.ingress.kubernetes.io/tags` |
| ALB 컨트롤러 SG (`[k8s] Managed SecurityGroup`) | Project·Environment만 | 위와 같음 |
| ALB 컨트롤러 SG (`[k8s] Shared Backend SecurityGroup`) | **0개** | 어노테이션이 이 SG에는 안 닿는다 |
| EKS 클러스터 SG | 비용 태그 없음 | infra `modules/eks/cluster.tf:48`이 붙이는 건 `karpenter.sh/discovery` 하나다(나머지 3개는 EKS가 붙인다) |
| PVC의 EBS 볼륨 | 해당 없음 | manifests에 PVC·`volumeClaimTemplate` 0건 |

노드(EC2·EBS)는 A·B 양쪽 다 덮였다. ALB 계열의 ManagedBy 누락은 아래 📌 계약과 규약서 §6-2 위반이고, 공유 backend SG는 어노테이션으로 닿지 않는다. 둘 다 배포팀 몫이다.

[확인 안 함] 비용 할당 태그 활성화가 과거 사용분에 소급되는지.

**③ 고아 사냥 필터가 Karpenter 노드를 못 걸러낸다.** `EC2NodeClass`가 노드에 `ManagedBy=terraform`을 박아서(위 표), Terraform이 만들지 않은 노드가 "태그 없는 것" 필터를 통과한다. destroy 후 잔존 노드는 이 필터에 안 보인다. 노드는 `karpenter.sh/nodepool` 태그 유무로 따로 센다.

### 3-4. 그러면 어떻게 관리하나 (3겹)
| 관리 방법 | 누가 | 무엇을 |
|---|---|---|
| **① 태그를 애초에 붙이기** | 인프라(A) + 배포팀(B) | (A) 노드그룹 EC2는 launch template `tag_specifications`로 태그 / (B) Karpenter `EC2NodeClass`의 `tags`, ALB Ingress 어노테이션 `alb.ingress.kubernetes.io/tags`에 Project·Environment·ManagedBy 지정 |
| **② 인클러스터 비용 배분** | 모니터링/배포팀 | **OpenCost** — AWS 태그와 별개로, 클러스터 비용을 네임스페이스·파드 단위로 쪼개 보여줌(K8s 워크로드 관점) |
| **③ 고아 자원 사냥** | 인프라 | `ManagedBy=terraform` 태그 **없는** 것 필터 → 잔여·수동 생성물 청소(특히 destroy 후). Karpenter 노드는 이 필터를 통과한다(§3-3) |

> 📌 **배포팀 계약사항:** 비용 태그(Project/Environment/ManagedBy)를 Karpenter·ALB 설정에도 동일 적용. 규약서 §6 태그 규약의 연장선.

## 4. 주요 비용원 — 끄면 아끼는 것들
> 요금은 리전·시점에 따라 다르니 **AWS 공식 요금표로 최종 확인**. 아래는 상대적 크기 감각용.

| 자원 | 과금 방식 | 메모 |
|---|---|---|
| **EKS 컨트롤플레인** | **클러스터당 시간요금** (안 써도 부과) | 데모 끝나면 destroy가 절감 최대 |
| **NAT Gateway** | 시간요금 + 데이터 처리요금 | 단일 NAT로 이미 최소화(규약서) |
| **RDS** t3.micro | 인스턴스 시간요금 (소액) | 24시간 켜두면 쌓임 |
| **EC2 노드** | Spot이라 저렴, 개수·시간 비례 | Karpenter가 한산하면 회수 |
| **EBS/스냅샷·EIP 미사용** | 붙어있지 않아도 과금 | 고아 자원 청소 대상(§3-4 ③) |
| **CloudFront** | 시간요금 없음. 요청수 + 전송량 비례 | 데모 트래픽 규모면 소액. `PriceClass_200`으로 엣지 범위를 좁혔다(`modules/edge/cloudfront.tf:63-64`) |

## 5. destroy 순서 — "지웠는데 콘솔에 남아있다"의 진실
`terraform destroy`는 **tfstate에 기록된 것만** 지운다. EKS가 돌 때 **K8s가 만든 AWS 자원(LB·노드·EBS)** 은 tfstate 밖이라 destroy로 안 지워지고 **계속 과금**된다.

엣지 기준 현재 상태(2026-07-25 실측): `enable_edge` 기본값이 `true`이고(`envs/dev/variables.tf:81`)
`alb_dns_name`에 ALB 실값이 들어가(`envs/dev/variables.tf:96`) 엣지 2단계까지 apply를 마쳤다.
ACM 인증서 2종·검증 레코드와 CloudFront·서비스 레코드 3종(apex·www·origin)이 모두 실재한다.

**배포팀 ALB는 2026-07-23에 생겼고 서울 인증서가 그 ALB의 HTTPS 443 리스너에 붙어 있다**(ACM `InUseBy`가 해당 ALB를 가리킨다 · 실측).
즉 1의 ALB 선행 삭제가 해당된다. Ingress를 안 지우고 destroy하면 3에서 인증서 삭제가 막힌다.
CloudFront도 실재하므로 3의 비활성화→삭제 2단계가 그대로 걸린다. 서비스 레코드 3종은 tfstate에 등재돼 있어
destroy가 함께 지운다. 생성 게이트는 `cloudfront_enabled`다(`modules/edge/route53.tf:5`·`:20` · `modules/edge/cloudfront.tf:16`).

**올바른 내리기 순서:**
1. 먼저 K8s 리소스 삭제 (Ingress → LB 회수, Deployment/PVC → 노드·EBS 회수)
   - 엣지를 쓰는 경우 Ingress(ALB) 삭제가 선행 조건이다. ALB 리스너에 붙은 ACM 인증서는 분리 전엔 삭제할 수 없어, ALB가 남아 있으면 3의 destroy가 인증서 삭제에서 실패한다.
   - **어떤 명령으로 지우느냐에 따라 결과가 갈린다. 명령을 정해 두고 시작한다.**

     manifests `origin/dev`의 ArgoCD Application 17개 중 **7개에**
     `finalizers: [resources-finalizer.argocd.argoproj.io]`가 없다(2026-07-28 실측).
     17개는 `argocd/applications/` 16개와 `argocd/app-of-apps.yaml` 1개다.

     | finalizer 있음 (10) | `app-of-apps` · `aws-load-balancer-controller` · `call-api` · `external-secrets` · `frontend` · `platform-secrets` · `predict` · `simulator` · `weather-cron` · `worker` |
     |---|---|
     | **없음 (7)** | `grafana-dashboards` · `karpenter` · `keda` · `kube-prometheus-stack` · `metrics-server` · `opencost` · `platform-monitoring` |

     | 명령 | 결과 |
     |---|---|
     | `argocd app delete` (기본 cascade) | **finalizer를 삭제 시점에 자동으로 붙인다**(Argo CD 문서 user-guide/app_deletion). 그래서 finalizer가 없는 7종도 하위 리소스까지 함께 지워진다 |
     | `kubectl delete application` | finalizer가 없으면 비-cascade다. Application 오브젝트만 사라지고 Karpenter 컨트롤러·NodePool·EC2NodeClass와 그것이 띄운 **노드·EBS가 고아로 남는다** |

     즉 1번의 "Deployment/PVC → 노드·EBS 회수"가 저절로 되는 것은 `argocd app delete` 경로뿐이다.
     `kubectl` 로 지우면 위 7종에서 새는다. **manifests `scripts/teardown_manifest.sh`의 삭제 줄이
     주석 처리돼 있어 팀의 실제 경로가 정해져 있지 않다.** 시작 전에 정한다.

     [확인 안 함] 삭제 때 sync-wave 역순이 지켜지는지는 Argo CD 공식 문서에 서술이 없다.
     순서를 wave에 기대지 말고 2번에서 눈으로 확인한다.

     `terraform destroy`는 ArgoCD를 아예 거치지 않는다. 클러스터를 통째로 지우므로 컨트롤러도
     같이 사라지고, ALB를 회수할 주체가 없어져 LB·타깃그룹·SG가 고아로 남는다. 그러면 서브넷 삭제도 막힌다.
     **어느 경로든 1은 사람이 직접 확인해야 한다.**
2. 컨트롤러(ALB Controller·Karpenter)가 자원 회수 완료됐는지 콘솔 확인
3. 그다음 `terraform destroy`
   - 엣지 자원(CloudFront·ACM 인증서 2종·검증 레코드·서비스 레코드)은 destroy가 지운다. CloudFront는 비활성화→삭제 2단계라 10분 이상 걸린다. 멈춘 게 아니니 기다린다.
   - ⚠️ **teardown을 시작하기 전에 CUR 버킷을 어떻게 할지 먼저 정한다. 안 정하면 destroy가 초반에 멈춘다.**

     `force_destroy = false`이고 버킷이 **이미 비어 있지 않다** — CUR 정의를 만들 때 AWS가 넣은
     `aws-programmatic-access-test-object`가 버킷 루트에 있고, lifecycle 3규칙 어디에도 안 걸려 영구히 남는다.
     그리고 의존성 그래프상 이 버킷은 destroy 순서에서 **앞쪽**이다(참조하는 관리 리소스가 자기 자식뿐이다.
     대조로 `module.eks.aws_eks_cluster.this`는 의존자가 11개다).
     그래서 `BucketNotEmpty`는 destroy **초반**에 난다. 비싼 자원이 내려간 뒤에 멈추는 것이 아니다.

     | 원하는 것 | 절차 (destroy 시작 **전에** 한다) |
     |---|---|
     | 비용 이력을 살린다 | ① `aws cur delete-report-definition --report-name hailcast-dev-cur --region us-east-1` ② `terraform state rm`으로 주소 6개를 state에서 뺀다(버킷·정책·lifecycle·public access block·암호화 설정·`random_id.cur_suffix`) ③ `terraform destroy`. 버킷은 IaC 밖 자원으로 남으므로 §5-9 표에 옮겨 적는다 |
     | 이력도 버린다 | ① 위와 같이 CUR 정의를 먼저 지운다(버킷을 먼저 지우면 CUR이 계속 배달을 시도해 오류만 쌓인다) ② `modules/storage/cur.tf`의 `force_destroy`를 `true`로 바꿔 apply ③ `terraform destroy` |

     ②의 apply는 **destroy를 시작하기 전에** 해야 한다. destroy가 이미 돌아 자원이 지워진 뒤에 apply하면
     EKS·NAT·RDS를 통째로 다시 만든다.

     살리는 쪽은 `scripts/teardown_infra.sh`가 대신 할 수 있다. `CUR_HANDLING=keep`이고 `CONFIRM=yes`일 때만이다
     (`:107` · `:109`). 둘 중 하나가 없으면 `:140`이 안 했다고 찍고 넘어간다. 버리는 쪽은 스크립트가 하지 않는다.
     `:143-147`에서 중단하고 사람에게 넘긴다.

     **①②를 스크립트에 맡기든 손으로 하든 둘 중 하나로 한다.** 섞으면 ①이 빠진다. `:128`이 state에 남아 있는
     주소만 고르고 `:133`의 CUR 정의 삭제가 `:132`의 "고른 주소가 있는가" 안에 있어서, ②만 손으로 먼저 하면
     스크립트가 `:137`로 빠져 ①을 건너뛴다. CUR 정의가 살아 있으면 버킷에 계속 파일이 들어온다.
   - **아티팩트 버킷은 반대다. 실패하지 않고 느려진다.** 두 버킷의 증상이 달라 대비도 다르다.

     `hailcast-dev-model-artifacts-*`는 `force_destroy = true`이고(`modules/storage/s3.tf:14`)
     버저닝이 켜져 있다(`:23-26`). destroy는 옛 버전까지 전부를 1000개씩 나눠 목록 조회하고 삭제한다.
     아래는 lifecycle을 넣기 전에 쌓이던 속도다.

     | 경과일(UTC 00:00 스냅샷 = KST 09:00) | 객체 수(옛 버전·삭제 마커 포함) | 버킷 크기 |
     |---|---|---|
     | 1일차 | 355 | |
     | 2일차 | 22,586 | |
     | 3일차 | 96,813 | |
     | 4일차 | 320,443 | 3.4GB |
     | 5일차 | 611,771 | 6.2GB |
     | 6일차 | 871,921 | 8.4GB |

     표는 닷새 구간이고, 최근 사흘은 하루 평균 26만 개씩 늘었다. **lifecycle 없이 이대로 가면**
     엿새 뒤에 약 240만 개 · 약 23GB이고, 1000개씩 끊어서 목록 조회와 삭제를 각각 2400번쯤 하게 된다.
     (CloudWatch `AWS/S3` `NumberOfObjects` `AllStorageTypes`·`BucketSizeBytes` `StandardStorage` 실측.
     이 지표는 나오는 데 시간이 걸려서 당일 값은 바로 안 보인다)

     **에러가 나는 게 아니라 그냥 오래 걸린다.** Terraform은 `Still destroying... [10s elapsed]`를
     계속 찍지만 몇 개나 지웠는지는 안 보여줘서, 얼마나 남았는지 알 방법이 화면에 없다.
     멈춘 줄 알고 중단하면 state와 실제 자원이 어긋난다. 기다린다.
     [확인 안 함] 실제로 얼마나 걸리는지는 재보지 않았다. 리허설 때 시각을 기록해 여기 채운다.

     **개수가 많은 파일과 용량을 차지하는 파일이 다르다.** 한쪽만 보면 엉뚱한 데를 고치게 된다.

     | 대상 | 버전 수 | 개수 비중 | 바이트 | 바이트 비중 |
     |---|---|---|---|---|
     | `traffic/instances/` | 655,544 | 58.8% | 44.6MB | 0.4% |
     | `simulator/status.json` | 227,859 | 20.4% | 66.6MB | 0.7% |
     | `dashboard/traffic.json` | 115,990 | 10.4% | 13.0MB | 0.1% |
     | `dashboard/traffic-history.json` | 115,981 | 10.4% | **9.97GB** | **98.4%** |
     | `dashboard/pod-history.json` | 105 | 0.0% | 0.6MB | 0.0% |
     | `models/` | 2 | 0.0% | 40.7MB | 0.4% |
     | `predictions/` | 90 | 0.0% | 0.07MB | 0.0% |
     | `weather/` | 29 | 0.0% | 0.06MB | 0.0% |

     (`aws s3api list-object-versions`로 버킷 전체를 센 값이다. 위 CloudWatch 표보다 하루 뒤에 재서
     총계가 하루치만큼 많고, 세는 방식도 달라 이 표에는 삭제 마커가 빠져 있다)

     개수가 많은 쪽은 `traffic/instances/`다. call-api 파드가 저마다 자기 샤드를 2초에 한 번
     덮어쓰고(app `backend/call-api/config.py:16`), predict도 같은 주기로 집계해서 `dashboard/`를
     다시 쓴다(app `backend/predict/config.py:40`). 두 값 다 `2.0`이다.

     용량은 `dashboard/traffic-history.json` 하나가 거의 전부다. 이 파일은 계속 커지는 게 아니라
     86KB에서 멈춰 있다(현재 86,402바이트 · 옛 버전 평균 86,004바이트. 이력을 1080개까지만 담는다 ·
     app `backend/predict/services/traffic_aggregator_service.py:15,66`). 그 크기 그대로 2초마다
     새로 써진다. `traffic/instances/` 샤드는 하나에 68바이트라, 샤드가 5.7배 많아도 용량은 224분의 1이다.

     여기에 더해 `traffic/instances/`에는 없어진 파드의 샤드가 그대로 남는다. 앱이 지우지 않는다.

     **lifecycle 규칙을 `modules/storage/s3.tf`에 넣어 뒀다.**
     `traffic/instances/`는 현재 버전 1일 + 옛 버전 1일, `dashboard/`와 `simulator/`는 옛 버전 1일이다.
     여기에 끊긴 멀티파트 업로드를 7일 뒤 정리하는 규칙이 하나 더 있다.

     `traffic/instances/`의 현재 버전 1일은 그렇게 남은 샤드를 지우려고 둔 것이다. 지금 세어 보면
     샤드 파일 89개 중 갱신되고 있는 것은 4개고 나머지는 야간 절전 때 멈춘 것들이다.
     위 표의 58.8%는 전부 옛 버전이고 그쪽은 `noncurrent_version_expiration`이 지운다.
     두 규칙이 지우는 대상이 다르다.

     `models/`·`weather/`·`predictions/`에는 규칙이 없다. 옛 버전이 쌓이지 않아 필요가 없다.

     **`expiration`은 현재 버전을 지우므로 프리픽스를 반드시 지정한다.** 프리픽스 없이 걸면
     `models/latest/model.pkl`이 지워진다. 그러면 `ModelLoader`가 `AwsError`를 내고
     (app `backend/predict/ml_runtime/model_loader.py:25,30` → `backend/common/aws/s3_adapter.py:61-66,110-114`),
     세 번 다시 시도한 뒤 `PredictionError`로 바뀌어 올라가며
     (app `backend/predict/services/prediction_service.py:49-62,70-72`), 스케줄러가 그것을
     실패 횟수와 `last_error`에만 적고 넘어간다(app `backend/common/core/scheduler.py:67-73`).
     파드는 Healthy로 보이고 예측만 멈춘다. 규약서 §5-3의 `exists()` 경우와는 다르다.

     `noncurrent_version_expiration`은 현재 버전을 건드리지 않아 이 문제가 없다. 멀티파트 정리 규칙도
     중간에 끊긴 업로드 조각만 지운다.

     **적용해도 버킷이 비지는 않는다.** `noncurrent_days`는 최솟값이 1일이라 0으로 못 줄이고,
     S3도 객체 하나당 하루에 한 번만 lifecycle을 적용한다. 옛 버전이 적어도 하루치는 남는다는 뜻이다.
     하루에 26만 개씩 늘고 있으니 26만 개 이상 · `traffic-history.json` 기준 2.3GB 이상이
     항상 남아 있다고 보면 된다(계산값). AWS가 삭제 시점을 언제까지 미룰 수 있는지 정해두지 않아
     더 남을 수도 있다. 무한정 늘어나는 것을 막는 것이지 버킷이 작아지는 게 아니다.
     용량을 더 줄이려면 86KB 파일을 2초마다 새로 쓰는 쪽을 고쳐야 하는데 그건 앱 소관이다.

     **2026-07-28에 apply했다.** `aws s3api get-bucket-lifecycle-configuration`으로 규칙 4개가
     Enabled인 것을 확인했다. 다만 객체가 언제부터 줄어드는지는 보장되지 않는다.
     위에 적은 대로 AWS가 삭제 시점을 미룰 수 있다. destroy 일정은 객체 수가 꺾인 것을 확인한 뒤 잡는다.
     설정이 S3 전체에 퍼지는 데도 시간이 걸려서, apply 직후에 바로 `plan`을 돌리면 한 번 변경이
     떴다가 사라질 수 있다(AWS provider 문서가 이 점을 명시한다). `No changes`를 화면에 띄워야 한다면
     apply와 시간 간격을 두고 확인한다.
4. 마지막으로 **콘솔에서 잔여 확인**: 미사용 EIP·EBS·스냅샷·ENI·LB
   - Route53 호스팅 영역은 destroy 후에도 남는 게 정상이다. Terraform이 만든 게 아니라 `data`로 조회만 한다(`modules/edge/main.tf:21` · 규약서 §5-7). NS 위임을 유지하려는 설계라 잔여 자원으로 오인해 지우지 않는다.

### 재구축 시 `hailcast-rds-secret`

Secret 이 없으면 call-api·predict·worker 가 CreateContainerConfigError 로 뜨지 못한다. 세 Deployment 가
`optional` 없이 참조한다(manifests `apps/call-api/deployment.yaml:56,65,70` ·
`apps/predict/deployment.yaml:55,60,65` · `apps/worker/deployment.yaml:34,43,48`).
클러스터를 새로 만들 때 이 Secret 이 채워지는 경로는 2026-07-28 에 바뀌었다.

**1번은 반드시 한다. 2번은 자동 경로가 생겨 확인 뒤에 판단한다.**

| 순서 | 할 일 | 왜 필요한가 |
|---|---|---|
| 1 | ESO CRD 를 `kubectl apply --server-side` 로 먼저 깐다 | 차트가 안 깐다. manifests `addons/external-secrets/values.yaml:5` 이 `installCRDs: false` 이고 레포에 설치 경로가 없다 |
| 2 | Secret 에 키 3개가 채워졌는지 확인한다. 안 채워졌으면 사람이 만든다 | ExternalSecret 두 개가 둘 다 `creationPolicy: Merge` 라 없는 Secret 을 만들지 못한다(manifests `platform/external-secrets/externalsecret-rds-credentials.yaml:15` · `externalsecret-rds-endpoint.yaml:15`). 빈 Secret 을 GitOps 가 만들어 두는 경로가 생겼다(아래) |

빈 Secret 은 manifests `platform/external-secrets/secret-rds-placeholder.yaml` 이 만든다(PR #58 · 2026-07-28 머지).
`:30` 이 이름을 `hailcast-rds-secret` 으로 두고 data 는 비운다. `:33` 의 sync-wave `-1` 로 ExternalSecret(기본 0)보다
먼저 적용된다. 둘 다 Application `platform-secrets` 안에 있다(manifests `argocd/applications/platform-secrets-app.yaml:15`).
ESO 가 채운 data 를 selfHeal 이 지우지 않도록 `:25` 의 `ignoreDifferences` 와 `:24` 의 `RespectIgnoreDifferences=true`
를 함께 건다.

[확인 안 함] 이 경로가 빈 클러스터에서 실제로 채워지는지는 확인하지 못했다. 재구축이 첫 실행이다.

```
kubectl -n hailcast get secret hailcast-rds-secret -o jsonpath='{.data}' | jq 'keys'
```

`["DB_HOST","DB_PASSWORD","DB_USER"]` 가 나오면 아래 명령은 건너뛴다. 키 이름은 규약서 §5-4 계약이라 바꾸지 않는다.

```
RDS_SECRET="$(terraform -chdir=envs/dev output -raw rds_master_secret_arn)"
CRED="$(aws secretsmanager get-secret-value --secret-id "$RDS_SECRET" --query SecretString --output text)"

kubectl create secret generic hailcast-rds-secret -n hailcast \
  --from-literal=DB_HOST="$(aws ssm get-parameter --name /hailcast/dev/rds/endpoint --query Parameter.Value --output text)" \
  --from-literal=DB_USER="$(echo "$CRED" | jq -r .username)" \
  --from-literal=DB_PASSWORD="$(echo "$CRED" | jq -r .password)" \
  --dry-run=client -o yaml | kubectl apply -f -
```

`create` 가 아니라 `apply` 로 흘린다. 빈 Secret 이 이미 있으면 `create` 만으로는 만들지 못한다.

app 레포 `scripts/deploy_infra.sh:138-142` 에도 같은 형태의 명령이 있다(값의 출처는 다르다. 스크립트는
`$RDS_HOST` 와 `$RDS_MASTER_SECRET_ARN` 을 쓴다). 다만 `:131` 이 Secret 이 없을 때만 실행하는 조건이라
빈 placeholder 가 있으면 존재로 판정해 건너뛴다. 이 경로로는 키가 안 채워진다.

`Merge` 를 `Owner` 로 되돌려서 풀지 않는다. manifests 커밋 `0c67287`(2026-07-22) 이 그 반대 방향으로 바꾼
커밋이고 메시지에 `target is owned by another ExternalSecret` 에러가 적혀 있다.

**Secret 이 없어진 날은 언제든 위 명령을 그대로 쓴다.** 야간 절전으로는 안 없어진다. 절전은 노드와 RDS 를
내리고 K8s 오브젝트는 남는다(2026-07-28 실측). 아침 점검 5번이 실패하면 기다리지 말고 실행한다
(manifests `scripts/morning/README.md:28`).

참고로 같은 클러스터에서 kube-prometheus-stack 은 더 큰 CRD(약 830KB)를 `ServerSideApply=true` 단독으로 깔아 Synced·Healthy 다.
ESO Application 은 `ServerSideApply` 와 `Replace` 가 함께 걸려 있고(manifests `argocd/applications/external-secrets-app.yaml:31-32`)
ArgoCD 문서상 Replace 가 우선한다. 첫 번째 원인의 근본 해결은 CRD 를 sync-wave 로 떼는 것보다 apply 방식 쪽일 수 있다(미확정).

## 담당 · 권한 메모
- **결제/Budgets 설정**: root·billing 권한 필요 → 계정 주인 몫일 수 있음.
- **apply/destroy**: CI(OIDC, **`hailcast-dev-gha-tf-apply`**, `infra-apply` environment 승인 후). `plan` 은 **`hailcast-dev-gha-tf-plan`**(읽기 전용)이 돌린다 — 규약서 §5-6.

- **태그 규약 전파**: 배포(manifests)팀이 Karpenter/ALB에 동일 태그 적용(§3-4).
- 이 문서는 인프라 담당이 유지관리하되, §3·§5는 배포팀과 공유 필요.

## 부록. tfstate 버킷 재부트스트랩 (재해복구)

지금 버킷(`hailcast-dev-tfstate-7dde`)이 살아 있는 동안은 필요 없는 절차다.
버킷을 잃었을 때(계정 이관, 오삭제) 다시 만드는 방법이며, README 현행화(#48) 때 걷어낸
초기 부트스트랩 기록을 여기로 옮겨 보존한다.

1. Terraform은 자기 상태 저장소를 스스로 못 만든다(닭과 달걀). 버킷 생성 단계만
   backend 없이(로컬 상태로) 부트스트랩한다.
2. S3 버킷 `hailcast-dev-tfstate-<랜덤4자>`를 만든다. 버저닝과 암호화를 켠다.
3. 잠금은 S3 자체 잠금(`use_lockfile = true`)이라 DynamoDB가 필요 없다. Terraform 1.11 이상.
4. 생성 후 실제 버킷 이름을 `envs/dev/backend.tf`와 `envs/dev/main.tf`의 `tfstate_bucket`에
   반영한다. 두 값은 같아야 한다(규약서 §5-6).
5. 기존 state 사본이 있으면(버저닝 복원, 로컬 백업) 새 버킷에 올리고 `terraform init -migrate-state`.
   사본이 없으면 리소스는 살아 있는데 state만 잃은 상태라 import 재구축이 필요하다. 대형 작업이라 팀 논의.
